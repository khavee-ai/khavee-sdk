## Current Focus

status: ROOT CAUSE CONFIRMED against live wp-env. The bug is more fundamental than the documented WR-01 JS-timing race: even if the nonce attached to the upload POST perfectly, the upload would STILL fail, because Plupload's CLIENT-SIDE mime filter (built once from get_allowed_mime_types() at settings-page GET render time) already lacks glb/vrm. No fix to the upload-POST nonce path alone can resolve this — the filter MUST be widened at the page-render moment, but the CR-02 nonce gate structurally cannot return true on a GET render (the nonce is emitted INTO the page, not carried TO it).

## Symptoms

expected: Clicking the "Choose/Upload Avatar" button opens the WP Media Library/uploader; uploading a real valid .vrm or .glb file succeeds and persists as the configured avatar (filename + upload date shown).
actual: "This file cannot be processed by the web server." for EVERY upload attempt — valid .glb, valid .vrm, a disguised renamed non-glTF file, and an oversized file ALL fail with this identical generic error. Nothing reaches our custom validation logic.
errors: "This file cannot be processed by the web server." (WordPress error shown in the Media Library frame)
reproduction: Test 5 in .planning/phases/07-admin-settings-page/07-UAT.md. Live wp-env at http://localhost:8888 (plugin active), admin user. Reproduced live in this session.
started: Discovered during Phase 07 UAT, immediately after the 07-04 gap-closure plan shipped (which added the CR-02 nonce gate to the upload-filter activation path).

## Root Cause

The CR-02 nonce gate (`is_khaveeai_upload_request()`) was introduced in 07-04 as an AND-clause on top of the existing admin_init + Referer + shutdown-cleanup filter-activation mechanism. It is implemented correctly as a fail-closed predicate AND it works exactly as designed — but its design contains an architectural flaw that breaks `.glb`/`.vrm` uploads at a point upstream of where it was intended to protect.

The flaw: `wp_plupload_default_settings()` (WP core, `wp-includes/media.php:4361`) builds the `_wpPluploadSettings.defaults.filters.mime_types[0].extensions` list by calling `get_allowed_mime_types()` and joining the keys. This JS object is emitted ONCE, into the page HTML, during the GET render of the settings page. Plupload (the JS uploader wp.media uses) then enforces this extension list CLIENT-SIDE in the browser — any file whose extension is not in the list is rejected with `plupload.FILE_EXTENSION_ERROR` BEFORE any HTTP upload POST is ever sent. Plupload maps `FILE_EXTENSION_ERROR` to the localized string `invalid_filetype` = **"This file cannot be processed by the web server."** (defined at `wp-includes/script-loader.php:1015`) — the EXACT UAT symptom string.

For Plupload's client-side list to include `glb`/`vrm`, the plugin's `upload_mimes` filter (`khaveeai_allow_glb_vrm_mimes`) must be REGISTERED at the instant `wp_plupload_default_settings()` runs during the GET render. But that filter registration is gated by `is_khaveeai_upload_request()`, which requires a valid `khaveeai_avatar_nonce` in `$_REQUEST`. A settings-page GET render NEVER carries that nonce — the nonce is generated by `wp_create_nonce()` and emitted INTO the page's inline JS (line 895); it is not a request parameter when LOADING the page. So on every GET render, `is_khaveeai_upload_request()` returns FALSE (proven live: `nonce_present=no is_upload_request_allowed=false`), the `upload_mimes` filter never registers, `get_allowed_mime_types()` returns the default WP list without `glb`/`vrm`, and `_wpPluploadSettings` is built without them. Plupload then rejects every `.glb`/`.vrm` selection client-side — for valid and invalid files alike, identically — matching the UAT report that EVERY file fails with the SAME generic message.

This means: (a) the WR-01 JS-timing race (the nonce failing to attach to the upload POST via `frame.on('ready')`) is NOT the operative bug, because the upload POST never happens in the first place — the file is rejected before it leaves the browser; and (b) even a perfect fix to the upload-POST nonce attachment would NOT resolve the symptom, because Plupload's filter was already frozen at page-render time without `glb`/`vrm`. The fix must ensure the `upload_mimes` filter is active when the settings PAGE RENDERS (the GET), not only on the upload POST.

## Hypotheses

### H1 (leading, from task brief): WR-01 — `frame.on('ready')` nonce-attachment JS race
The nonce fails to reach the upload POST because wp.media's `frame.uploader` sub-view doesn't exist when the frame's `'ready'` event fires. **RESULT: REFUTED as the OPERATIVE cause.** The upload POST never happens — Plupload rejects the file client-side before any POST. WR-01 may still be a real (secondary) latent bug, but it is NOT what produces the UAT symptom. Proven by: the rendered `_wpPluploadSettings` lacks `glb`/`vrm` (so Plupload blocks client-side), and the symptom string maps to Plupload's `FILE_EXTENSION_ERROR`, not to a server response.

### H2 (the ACTUAL root cause): CR-02 nonce gate returns false on the settings-page GET render, so `upload_mimes` is never widened at the moment Plupload's filter is built
The filter-activation gate requires a nonce that a GET render cannot carry. **RESULT: CONFIRMED.** Proven by live instrumentation: on the settings-page GET, `page_or_referer_match=true` but `nonce_present=no` → `is_upload_request_allowed=false`. And `_wpPluploadSettings` rendered without `glb`/`vrm`. Conversely, on a simulated upload POST WITH the nonce, the gate correctly returns `true` (`nonce_present=yes is_upload_request_allowed=true`) — proving the gate logic itself is sound; the bug is that the gate runs at the wrong request-lifecycle moment for this purpose.

### H3 (alternative considered): The nonce DOES reach the upload, filters DO register, but `khaveeai_validate_glb_vrm_content()`/`khaveeai_allow_glb_vrm_mimes()` reject a valid file for another reason (magic-byte check, MIME, server config)
**RESULT: REFUTED.** Our custom filter logic never executes for these uploads — the file is rejected by Plupload in the browser before reaching the server. (The `wp_check_filetype_and_ext` magic-byte validator is also never reached for the same reason.) Disproven by: Plupload's `FILE_EXTENSION_ERROR` is client-side; the rendered `_wpPluploadSettings` proves the rejection happens at selection time in the browser.

## Eliminated Hypotheses

- **WR-01 (`frame.on('ready')` JS nonce-attachment race) as the OPERATIVE cause** — refuted. Even with perfect nonce attachment on the upload POST, Plupload would still reject `.glb`/`.vrm` client-side because `_wpPluploadSettings` was built without them at page-render time. (WR-01 may remain a latent secondary bug worth fixing defensively, but it does not produce this symptom.)
- **Our magic-byte validator / MIME filter rejecting valid files** — refuted. Neither `khaveeai_validate_glb_vrm_content()` nor `khaveeai_allow_glb_vrm_mimes()` ever executes for these uploads; Plupload blocks the file in the browser before any server-side filter runs.

## Suggested Fix Direction

The fix must ensure the `upload_mimes` filter is active when the settings PAGE RENDERS (so Plupload's client-side list includes `glb`/`vrm`), WITHOUT weakening the CR-02 spoofable-activation concern. The cleanest options for the gap-closure planner to evaluate:

1. **Widen the gate's "page render" branch to also register the `upload_mimes` filter (but NOT the magic-byte `wp_check_filetype_and_ext` filter) on a plain settings-page GET.** The `upload_mimes` widening is safe to apply on the GET because: (a) the GET is already `manage_options`-gated (the menu + `render_page()`'s capability re-check), so only admins see the widened list; (b) widening `upload_mimes` alone does NOT bypass the magic-byte check — `khaveeai_validate_glb_vrm_content()` remains nonce-gated on the upload POST, so a disguised file still gets rejected server-side even if Plupload lets it through. This cleanly separates the two concerns: "Plupload client-side allowlist" (needs to be widened at GET render) vs "server-side content validation" (correctly stays nonce-gated on the POST).

2. **Alternatively, register `khaveeai_allow_glb_vrm_mimes` on a broader but still-safe condition** — e.g. whenever `current_user_can('manage_options')` AND the request is the settings-page GET (page query var matches) — keeping the nonce gate for the `wp_check_filetype_and_ext` magic-byte filter as 07-04 intended. This is essentially option 1 stated differently.

3. **A cleaner long-term redesign:** pass `library: { type: 'model/gltf-binary' }` already exists on the frame constructor (line 908) but that only filters the library DISPLAY, not the upload filter. Consider also passing the allowed extensions into the wp.media frame's `uploader` config at construction (Plupload honors a frame-level `filters.mime_types` override), bypassing the global `_wpPluploadSettings` entirely for this frame instance — but this is more invasive and the security implications need a fresh review.

NOT sufficient (would NOT fix the symptom): any fix that only touches the upload-POST nonce path (e.g. fixing WR-01 by attaching the nonce via the frame constructor's `uploader.params` instead of `frame.on('ready')`). Such a fix would make the upload-POST nonce arrive reliably, but Plupload would still reject the file client-side before the POST fires. The fix MUST widen `get_allowed_mime_types()` at page-render time.

## Blind Spots / Notes

- The wp-cli `eval-file` context could NOT faithfully reproduce a browser nonce-verify (`wp_verify_nonce` returned false for a nonce generated in the same eval, because wp-cli lacks the browser cookie session). This affected only my secondary positive-case test, not the primary findings. The authoritative positive-case evidence is the `async-upload.php` POST test, which ran in the real browser-equivalent session context and showed `is_upload_request_allowed=true` with the nonce present.
- I did not exhaustively test whether Plupload's client-side filter is the ONLY block, or whether (if a user disabled JS / used the HTML fallback uploader) the server-side path would also need `glb`/`vrm` in `upload_mimes` at POST time. Option 1 above covers both, because it registers `upload_mimes` on the GET and the existing nonce-gated path covers the POST.
- The HTTP 403 observed on the simulated upload POST was WP core's own `media-form` nonce failing under curl's session context — a test artifact, NOT our plugin. It does not affect the conclusion (our gate returned true, which is what was under test).
