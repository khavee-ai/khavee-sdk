## vrm-parse-hang-in-editor — VRM avatar invisible in Gutenberg block editor preview, misdiagnosed as a parse hang
- **Date:** 2026-07-09
- **Error patterns:** VRM, avatar, block editor, preview, invisible, never appears, no error, avatarScale, lightIntensity, resolveSceneDefaults, Gutenberg schema default, zero scale, "Waiting for animations or VRM to load", GLTFLoader, VRMLoaderPlugin, iframe editor-canvas
- **Root cause:** packages/wp-bundle/src/config.ts's resolveSceneDefaults() resolved avatarScale/lightIntensity with `c.avatarScale ?? 1.0` / `c.lightIntensity ?? LIGHT_INTENSITY.default`. Gutenberg's block.json attribute schema defaults these numeric sliders to 0, and Gutenberg ALWAYS populates the attribute with this schema default even when the author never touches the slider — so the incoming value is a real, present 0, never null/undefined, and `??` cannot catch it. This resolved avatarScale=0 -> <VRMAvatar scale={[0,0,0]}> in the editor preview: the model fetches, parses, and mounts successfully (no hang anywhere in the load chain), but renders at zero size, visually indistinguishable from "never loaded." The published front-end path was already immune because wordpress-plugin/includes/Block/AvatarBlock.php's render_callback applies the same "0 means unset" sentinel (`> 0 ? (float) $attributes['avatarScale'] : null`, with null stripped so wp_parse_args' real default wins) — that fix (dated 2026-07-02) was never mirrored into the client-side JS resolveSceneDefaults() used by the editor preview. The "[VRM Animation] Waiting for animations or VRM to load..." log that appeared to loop forever was a red herring, unrelated to VRM/parse state (fires whenever the `animations` prop is falsy, e.g. IDLE_ANIMATION_URL unset), and only fired once per mount.
- **Fix:** Changed resolveSceneDefaults() to treat avatarScale/lightIntensity <= 0 as "unset" (mirroring AvatarBlock.php's `> 0` convention) instead of using `??`: `avatarScale: c.avatarScale && c.avatarScale > 0 ? c.avatarScale : 1.0` and `lightIntensity: c.lightIntensity && c.lightIntensity > 0 ? c.lightIntensity : LIGHT_INTENSITY.default`. Rebuilt wordpress-plugin/build/khaveeai-preview.js.
- **Files changed:** packages/wp-bundle/src/config.ts, wordpress-plugin/build/khaveeai-preview.js (rebuilt artifact)

## camera-framing-mismatch — Gutenberg editor preview shows head+shoulders crop instead of full body, only on Retina/dpr!=1 displays
- **Date:** 2026-07-10
- **Error patterns:** camera, framing, headshot, crop, full body, editor preview, published page mismatch, devicePixelRatio, dpr, Retina, HiDPI, canvas style, instanceof HTMLCanvasElement, cross-realm, iframe editor-canvas, react-three-fiber Canvas resize, WebGLRenderer.setSize, canvas.style.width, getBoundingClientRect, PreviewAvatarCanvas, editorScript top window
- **Root cause:** Two independent camera-path defects were found; only the second was the actual cause of the reported symptom. (1) react-three-fiber's Canvas hardcodes `camera.lookAt(0,0,0)` once at creation when the `camera` prop has no explicit `rotation` — mount.tsx's published-page path never corrected this afterward while PreviewAvatarCanvas.tsx already did via CameraController + OrbitControls; a real (~2.5deg) divergence but proven NOT the cause of "headshot vs full body" via direct runtime camera-state measurement (position/rotation/fov/aspect identical between contexts after this fix). (2) The actual root cause: a devicePixelRatio-gated CSS-sizing bug, invisible at dpr=1 (why repeated headless self-verification at default dpr found nothing) and 100% reproducible at dpr=2. @react-three/fiber's Canvas-resize code decides whether to apply `canvas.style.width/height` via `gl.domElement instanceof HTMLCanvasElement` (node_modules/@react-three/fiber/dist/events-*.cjs.dev.js). WordPress's block.json `editorScript` (khaveeai-preview.js) is never injected into the Gutenberg block-canvas iframe — it executes in the TOP wp-admin window's JS realm — while its React root mounts a `<div data-khaveeai-preview-config>` that physically lives INSIDE `iframe[name="editor-canvas"]`, a separate document/realm. The `<canvas>` DOM node React creates therefore belongs to the iframe's realm, so this cross-realm `instanceof HTMLCanvasElement` check (against the top window's constructor) always evaluates false, `updateStyle` becomes false, and `WebGLRenderer.setSize()` never sets the canvas's CSS style. The canvas falls back to its intrinsic size (its width/height HTML attributes, correctly `containerCSSSize * devicePixelRatio`) interpreted directly as CSS pixels — at dpr=1 this numerically equals the correct size (bug invisible); at dpr=2 the canvas renders at exactly 2x its intended CSS footprint, producing the head+shoulders crop, only in the editor/iframe context (the published page's mount point shares its own script's document realm, so the instanceof check succeeds there).
- **Fix:** (1) Shared `packages/wp-bundle/src/CameraController.tsx` used by both mount.tsx and PreviewAvatarCanvas.tsx to imperatively re-aim the camera at `scene.cameraTarget` (retained, valid, but not the fix for the reported symptom). (2) Added `CanvasStyleSync` to `packages/wp-bundle/src/preview/PreviewAvatarCanvas.tsx` — a small sibling component (mirrors the existing CameraController/CameraRefCapture pattern) that reads R3F's own already-correct `size` state via `useThree()` and unconditionally applies it to `gl.domElement.style.width/height` on every size change, bypassing the broken cross-realm `instanceof` gate entirely rather than patching node_modules or trying to avoid the realm split (required by WordPress's own editorScript-in-top-window constraint). Scoped to PreviewAvatarCanvas.tsx only; PreviewFloatingWidget.tsx reuses this same component so it needed no separate change. mount.tsx (published page) needs no equivalent fix since it already shares its own script's document realm.
- **Files changed:** packages/wp-bundle/src/CameraController.tsx, packages/wp-bundle/src/mount.tsx, packages/wp-bundle/src/preview/PreviewAvatarCanvas.tsx, wordpress-plugin/build/khaveeai-bundle.js, wordpress-plugin/build/khaveeai-preview.js
