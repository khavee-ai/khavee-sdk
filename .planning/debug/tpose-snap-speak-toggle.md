## Current Focus

reasoning_checkpoint:
  hypothesis: "`beginCrossfade` (packages/react/src/animation/crossfade.ts) unconditionally forces the incoming `toAction`'s weight to exactly 0 and assumes the outgoing `fromAction` ramps down from exactly 1, regardless of either action's ACTUAL current effective weight. Whenever `switchToClip` interrupts an already-in-progress crossfade (calls `beginCrossfade` again before the previous blend's `stepCrossfade` reaches t>=1), the new `toAction` is frequently the PREVIOUS blend's `fromAction` (or another action that was already contributing real weight) — forcing it to 0 while `stepCrossfade` for the new blend hasn't run yet for the current frame causes total accumulated mixer weight across all bound actions to drop well below 1 for at least one rendered frame (since `mixer.update()` runs BEFORE `controller.update()`/`stepCrossfade` in VRMAvatar's per-frame order). THREE's PropertyMixer fills that weight shortfall with the bind/original pose, producing the visible T-pose/bind-pose flash, exactly at clip-switch boundaries (entering/exiting speaking, or talk-cycle variant switches) — which is precisely when interruption is most likely."
  confirming_evidence:
    - "crossfade.ts beginCrossfade(): `toAction.setEffectiveWeight(0)` is unconditional — never reads toAction.getEffectiveWeight()/isRunning() first, even though toAction may already be actively contributing weight (e.g. it was the `from` of a blend interrupted moments ago)."
    - "crossfade.ts stepCrossfade(): `blend.from?.setEffectiveWeight(1 - eased)` hardcodes the outgoing action's start weight as 1; when `fromAction` is itself the incoming leg of a just-interrupted blend (e.g. weight 0.216 mid-ramp), this formula is wrong for t=0 (assumes 1, not 0.216) — the true value is only reached asymptotically, not seeded."
    - "VRMAvatar.tsx useFrame (line ~561-583): `mixer.update(delta)` runs BEFORE `controller.update(delta)` every frame — confirmed by reading the component's useFrame callback directly. AnimationStateEngine.ts's chatStatus-driven useEffect ([targetName, chatStatus] deps) commits on React's own schedule, independent of rAF/useFrame ticks — so a switchToClip call from that effect can force toAction's weight to 0 and leave fromAction's stale weight untouched for at least one full mixer.update() pass before controller.update()'s stepCrossfade gets a chance to correct it."
    - "talkCycle.ts (TALK-01) now fires additional switchToClip calls mid-speaking (loop-boundary + MIN_TALK_DWELL_SECONDS=2.0s) whenever 2+ speaking-pattern clips exist (speakingVariants.length >= 2) — with only 1 talk clip (Phase 10/pre-upgrade config), there was exactly ONE crossfade per speaking session (idle->talking), which reliably had 0.3-0.9s to fully settle before a typical speaking session ended, so interruption was never exercised/verified. With 3 concurrent talk clips (talking/talking1/talking2), multiple crossfades now occur per speaking turn, sharply raising the odds that chatStatus flips into/out of 'speaking' (or a talk-cycle variant switch itself) lands while a PRIOR crossfade is still in flight — i.e. an interrupted crossfade, exactly the untested case."
    - "No existing test in crossfade.test.ts or AnimationStateEngine.test.ts exercises beginCrossfade being called a SECOND time while the FIRST blend is still active (t<1) — all existing 'second switch' tests (e.g. AnimationStateEngine.test.ts's G2-fix test) always let the first blend run to completion (t>=1) before starting the second, which is exactly why this defect was never caught."
  falsification_test: "Write a unit test that: (1) beginCrossfade(null, A) and step to a PARTIAL weight (t=0.3, A not yet fully settled); (2) immediately beginCrossfade(A, B) (interrupt, mirroring switchToClip's real call pattern) WITHOUT calling stepCrossfade first; (3) read A.getEffectiveWeight() and B.getEffectiveWeight() at that exact instant (before any stepCrossfade call for the new blend). If the hypothesis is correct, B's weight will be forced to 0 while A's weight remains at its stale partial value (e.g. ~0.784 for the outgoing-from-blend-1 case) rather than a settled 1 -- meaning total weight sums to well under 1, not ~1. If instead A+B sum to ~1 at that instant, the hypothesis is refuted and the snap must come from elsewhere (e.g. an orphaned third action, or the resetToRestPoseIfNotDriven gate)."
  fix_rationale: "Seed `toAction`'s starting weight in beginCrossfade from its OWN current effective weight (via `isRunning()`/`getEffectiveWeight()`) instead of a hardcoded 0, and generalize stepCrossfade's ramp math to interpolate from each action's ACTUAL captured start weight (stored on BlendState) toward its target (1 for `to`, 0 for `from`) instead of assuming to-starts-at-0/from-starts-at-1. This preserves total accumulated weight continuity across an interruption instead of introducing a one-frame weight-sum cliff. Additionally, switchToClip must explicitly `.stop()` the PREVIOUS blend's `from` action when it is about to be orphaned (i.e. not reused as the new toAction) — otherwise, in 3+-deep interruption chains (idle->talking->talking1->[interrupt to idle]), the original blend's `from` (e.g. plain 'talking') is never referenced by the new blend and never completes/stops, so it keeps contributing its last weight to the mixer forever, uncoordinated with the new blend. This addresses the root cause (an unconditional-weight-reset assumption baked into the crossfade engine that was never wrong until interruption became likely) rather than a symptom (e.g. papering over it with an extra rest-pose reset, which would just trade an under-driven flash for a different discontinuity, as 11-09's whole-block-skip approach already proved for a related case)."

## Resolution

root_cause: "beginCrossfade()/stepCrossfade() (packages/react/src/animation/crossfade.ts) assume every crossfade starts clean (`to` at weight 0, `from` at weight 1) and never account for either action already being mid-ramp when a crossfade is interrupted by a new switchToClip call before the prior blend reached t>=1. Because VRMAvatar's mixer.update() runs one frame-slice before controller.update()'s stepCrossfade can correct the freshly-forced weight, an interrupted crossfade produces at least one rendered frame where total accumulated action weight is well under 1, which THREE's AnimationMixer/PropertyMixer fills with the bind pose — the reported T-pose/bind-pose flash. A second, compounding defect: on a 3+-deep interruption chain (idle -> talking -> talking1 -> [interrupted back to idle]), the middle blend's outgoing action (e.g. plain 'talking') is referenced by no BlendState going forward and is never `.stop()`-ed (stepCrossfade only stops `from` at natural t>=1 completion), so it would keep contributing its last stale weight to the mixer indefinitely. Newly exposed (not introduced) by Phase 11's talk-cycle variant switching now firing multiple crossfades per speaking turn once 2+ concurrently-matching talk clips exist (talking/talking1/talking2), sharply raising the odds that a chatStatus toggle or variant switch lands mid-blend — with only 1 talk clip (pre-upgrade), exactly one crossfade occurred per speaking turn with ample time to settle, so this path was never exercised/verified."
fix: "Two changes, both in packages/react/src/animation/: (1) crossfade.ts's BlendState gained fromStartWeight/toStartWeight fields; beginCrossfade() now seeds toAction's start weight from its own actual current weight (via isRunning()/getEffectiveWeight()) instead of a hardcoded 0, and stepCrossfade()'s ramp math generalizes to interpolate from each action's captured start weight toward its target (reduces to the exact original formula in the non-interrupted case). (2) AnimationStateEngine.ts gained an exported pure function resolveOrphanedBlendAction(prevBlend, toAction) that identifies when a previous blend's `from` action is about to be orphaned by a new switch (referenced by no BlendState going forward) and returns it so switchToClip can explicitly .stop() it, preventing it from contributing stale weight forever."
verification: "Self-verified: (1) wrote a failing repro test first (crossfade.test.ts) proving total weight dropped from ~1 to ~0.108 when an interrupted crossfade forced the incoming action's weight to 0 while the outgoing one kept its stale partial weight — confirmed red before the fix; (2) applied the fix; (3) same test now passes (total weight stays continuous across the interruption); (4) added resolveOrphanedBlendAction unit tests (pure-function cases) plus a 3-deep interruption-chain integration test proving the orphaned action is explicitly stopped rather than left dangling; (5) full animation test suite: 158/158 passing (up from 149 baseline — 9 new tests, 0 regressions); (6) `npx tsc --noEmit` and `npx tsc` (package build) both clean with no errors. GLBAvatar.tsx shares the same useAnimationController/crossfade engine (grep-confirmed, no separate wiring), so it receives the fix automatically with no separate changes needed. NOT YET verified live in khavee-app's browser Preview page — requires human checkpoint."
