<!-- The two tool shapes (source of truth) and the exact current mechanics being fixed. -->

Tool (vendor-neutral, what the LLM is offered) — packages/core/src/types/tools.ts:29-45:
  interface Tool {
    name: string;
    description: string;
    parameters: {
      type: "object";
      properties: Record<string, { type: "string"|"number"|"boolean"|"array"|"object"; description?: string; enum?: string[] }>;
      required?: string[];   // TOP-LEVEL array of required property names
    };
    execute: (args: any) => Promise<ToolResult>;
  }

RealtimeTool (legacy, what registerFunction receives) — packages/core/src/types/realtime.ts:7-22:
  interface RealtimeTool {
    name: string;
    description: string;
    parameters: {
      [key: string]: {       // map of property-name → descriptor
        type: "string"|"number"|"boolean"|"array"|"object";
        required?: boolean;  // PER-PROPERTY boolean
        enum?: string[];
        description?: string;
      };
    };
    execute: (args: any) => Promise<{ success: boolean; message: string }>;
  }

Structural incompatibility (already documented at GenericPipelineConfig doc comment, GenericPipelineProvider.ts:38-46): RealtimeTool.parameters is a flat map of descriptors with per-property `required?: boolean`; Tool.parameters is `{ type:"object", properties:{...}, required?: string[] }`. tsc rejects unifying them. The fix CONVERTS, it does not widen/narrow.

Conversion shape (RealtimeTool → Tool):
  - Tool.name = RealtimeTool.name; Tool.description = RealtimeTool.description; Tool.execute = RealtimeTool.execute (same `(args)=>Promise<{success,message}>` shape, assignable to ToolResult).
  - Tool.parameters = { type: "object", properties, required } where:
      properties[key] = { type, description, enum } (drop the per-property `required` boolean when building properties)
      required = the array of keys whose descriptor had `required === true` (omit/empty-array if none).

CURRENT registerFunction (GenericPipelineProvider.ts:156-158) — DEFECTIVE:
  registerFunction(tool: RealtimeTool): void {
    this.toolExecutor.register(tool.name, tool.execute);   // dispatch half only — never offered to LLM
  }

CURRENT constructor tool wiring (GenericPipelineProvider.ts:139-140):
  this.toolExecutor = new ToolExecutor();
  config.pipelineTools?.forEach((tool) => this.toolExecutor.register(tool.name, tool.execute));
  (pipelineTools are routed to ToolExecutor here, but the array offered to the LLM is read straight off this.config.pipelineTools — there is no runtime-mutable list yet.)

CURRENT LLM call site (GenericPipelineProvider.ts:432-437) inside runTurnFromText:
  result = await this.llm.complete({
    messages: this.messages,
    tools: this.config.pipelineTools,   // construction-time only — must read combined runtime list instead
    signal,
  });

The fix introduces a private runtime-mutable list (e.g. `private pipelineToolList: Tool[]`) seeded from `config.pipelineTools` at construction; registerFunction pushes a converted entry onto it AND keeps the existing ToolExecutor.register call; runTurnFromText's tools: field reads `this.pipelineToolList`.
