The defect: the bounded multi-round tool-calling loop in `GenericPipelineProvider.runTurnFromText` (lines ~493-530) executes tool calls and pushes only a `role: "user"` tool-result marker message (`[tool_result id=<id> name=<name>] <content>`) into `this.messages` for each round. Every OpenAI-compatible Chat Completions backend requires a `role: "tool"` message to be immediately preceded by the assistant message bearing the matching `tool_calls` entry — a request missing it is rejected with HTTP 400. This breaks round 2+ of ANY real multi-round tool-calling conversation (D-04/D-05, an explicit tested must-have of this phase), and is in the critical path of Phase 5's planned demo (even a single tool call requires a round-2 `complete()` call).

It is invisible to the existing D-04/D-05 tests because their fake LLM (`complete: vi.fn().mockImplementation(...)`) ignores `args.messages` entirely — round-counting is done via a closure variable, not by inspecting what was sent.

Purpose: make ORCH-01's multi-round tool-calling contract actually correct against a real vendor backend, and add a test that validates the message-history shape sent on round 2 (instead of ignoring it).
