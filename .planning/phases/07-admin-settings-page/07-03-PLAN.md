<objective>
Add the avatar upload to the settings page built in 07-02, implementing the **two-filter** VRM/GLB content validation (D-09, ASSET-01) and explicitly resolving RESEARCH.md Open Question 2 / Assumption A2: the `upload_mimes` and `wp_check_filetype_and_ext` filters MUST fire on BOTH of WordPress's two distinct avatar-upload AJAX paths — (a) the `options.php` settings-save POST and (b) `wp.media`'s own `async-upload.php`/`wp_ajax_upload_attachment` handler — because the actual binary upload happens via path (b) the moment the admin picks a file in the wp.media frame, BEFORE the settings form is ever submitted.

Purpose: This plan closes ASSET-01 (the highest-severity security surface in the phase — disguised-file upload via extension-trusting) and SET-04, and re-asserts SET-05 for the avatar upload path specifically. It also completes D-11 (filename + upload date display, no live 3D preview) and D-10 (50MB plugin-level limit). It depends on 07-02 because it inserts into SettingsPage.php at the marked insertion point and reuses the same capability gate.

Output: Modified `SettingsPage.php` (avatar field added at 07-02's marked insertion point; two scoped filter callbacks; Remove-avatar control; 50MB enforcement; inline wp.media JS), extended `settings-page-harness.php` (magic-byte check cases), and a human-checkpoint verification against a live WP install (the only way to truly confirm the wp.media AJAX path is covered — Assumption A2).
</objective>
