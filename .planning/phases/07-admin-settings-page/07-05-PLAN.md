<objective>
Close the single UAT-confirmed major bug from Phase 7's UAT (07-UAT.md Test 5, root-caused in `.planning/debug/avatar-upload-rejected.md`): every valid `.glb`/`.vrm` avatar upload through the settings-page Media Library picker fails with "This file cannot be processed by the web server." Tests 6, 7 surfaced the same upstream symptom (same generic error for disguised/oversized files); Test 8 was blocked by it.

**Root cause (proven live against wp-env):** Plupload (wp.media's client-side uploader) builds its file-extension allowlist from `get_allowed_mime_types()` ONCE at settings-page GET render time (`wp_plupload_default_settings()`, WP core `wp-includes/media.php`). The plugin's `khaveeai_allow_glb_vrm_mimes` (`upload_mimes` filter, which adds glb/vrm) is gated behind `is_khaveeai_upload_request()` → `is_upload_request_allowed()`, which requires the `khaveeai_avatar_nonce` in the request. A GET render NEVER carries that nonce (it is emitted INTO the page, not sent TO it), so the gate returns false on the GET, `upload_mimes` never registers, `get_allowed_mime_types()` returns defaults without glb/vrm, and Plupload rejects every `.glb`/`.vrm` CLIENT-SIDE (`plupload.FILE_EXTENSION_ERROR`, localized as "This file cannot be processed by the web server.") before any upload POST fires. The file never reaches the server — so neither the WR-01 nonce-attachment JS race nor the magic-byte validator is the operative cause.

**The fix — separate the two filters by their distinct lifecycle needs:**

1. `upload_mimes` filter — widens Plupload's CLIENT-SIDE extension allowlist. Must be active at GET-render time. Safe to gate on `current_user_can('manage_options')` + page-match ONLY (it does NOT bypass server-side content validation — a disguised file is still rejected by the magic-byte check on the POST).
2. `wp_check_filetype_and_ext` (magic-byte) filter — the real server-side ASSET-01 content validation. MUST stay nonce-gated on the upload POST via `is_khaveeai_upload_request()`, exactly as 07-04 built it. UNCHANGED.

A fix targeting only the WR-01 nonce-attachment JS timing would NOT resolve this symptom — Plupload still rejects client-side. WR-01 remains a separate, non-blocking open item (07-SECURITY.md) and is NOT addressed by this plan.

Purpose: Move Phase 7's avatar-upload UAT truth from FAILED to PASS by ensuring the `upload_mimes` filter is active at the GET render so Plupload's client-side list includes `glb`/`vrm` — WITHOUT weakening the CR-02 nonce-gated server-side magic-byte defense (which must stay scoped to the upload POST) and WITHOUT reintroducing the empirically-falsified `load-<hook_suffix>` mechanism (07-03 Deviation 2).
Output: Modified `SettingsPage.php` (separated filter-registration conditions; `upload_mimes` on the GET-render path, `wp_check_filetype_and_ext` + `upload_size_limit` unchanged on the nonce-gated POST path), extended `settings-page-harness.php` (cases proving the new GET-render-time registration condition), and the existing Wave 5 bullet in `.planning/ROADMAP.md` flipped from `[ ]` to `[x]` on completion.
</objective>
