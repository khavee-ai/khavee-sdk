# Phase 9 — UI Design Contract

> Visual and interaction contract for the Block Studio phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This contract covers TWO distinct, non-overlapping UI surfaces plus a shared runtime. Each has its own token application:

- **Surface 1 — WP Inspector (Part A):** the Gutenberg `InspectorControls` sidebar. Rendered with native `@wordpress/components` (`PanelBody`, `RangeControl`, `SelectControl`, `ToggleControl`, `TextControl`, `ColorPalette`, `MediaUpload`, `FocalPointPicker`-style selects). Inherits wp-admin styling. This surface is authored in `wordpress-plugin/src/editor.js` using `createElement` (no JSX, no React-DOM import) — exactly as Phase 8 did.
- **Surface 2 — Editor Preview (Part B):** a SAFE live 3D preview mounted by the bundle's new `editorScript` preview-mode entry into the editor canvas iframe. Renders VRM + scene + config but NO mic, NO token, NO realtime provider.
- **Surface 3 — Published Frontend (Parts C + D live here):** the existing `viewScript` live SPA, extended to consume the new visual/chat config from `data-khaveeai-config` and host the ChatBox + real lip-sync.

Token precision matters most on Surfaces 2 and 3 (the bespoke-CSS bundle). Surface 1 inherits wp-admin's own scale and only needs *copywriting + interaction-state* precision — its visual tokens are wp-admin's, not ours.

## Spacing Scale

Declared values (multiples of 4). These apply to **bundle-authored CSS** (ChatBox, editor-preview chrome, updated `.khaveeai-root` layout). The inspector's spacing is WP core's own (`PanelBody` padding etc.) and is NOT re-tokenized here.

| Token | Value | Usage (this phase) |
|-------|-------|--------------------|
| xs | 4px | ChatBox: gap between inline elements (send-button icon inside input, message-bubble text to bubble edge inner padding); inspector panel-row label-to-control gap is wp-admin's, not this token |
| sm | 8px | ChatBox: gap between consecutive message bubbles; editor-preview banner: padding between title and subtitle |
| md | 16px | ChatBox: message bubble inner padding (all sides); ChatBox header/footer vertical padding; gap between the avatar canvas region and the ChatBox region when placement = "beside"; editor-preview banner padding |
| lg | 24px | ChatBox: outer padding around the whole ChatBox card; editor-preview: padding inside the dashed editor-preview container when no model is set |
| xl | 32px | Published container: minimum height reserved for the avatar canvas before the model finishes loading (layout-shift guard, carries forward Phase 8's `min-height` intent) |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

Exceptions:
- **Touch-target floor = 44px height** for the ChatBox send button and any toggle button rendered in the published widget (accessibility floor for primary affordances on a small-screen embed). 44 is a fixed touch-target exception, not a spacing token. Carries forward Phase 8's identical exception.
- **Inspector control heights** are wp-admin's own (`RangeControl`, `SelectControl` etc. come pre-sized by WP core) and are intentionally NOT re-tokenized — re-tokenizing them would fight the host admin theme.
- The 3D canvas itself is not CSS-spaced; its framing is set by the **camera preset** and **avatar scale/offset** knobs (Part A), expressed in three.js world units, not pixels.

## Color

Carries forward Phase 8's embed-aware color contract (dominant = transparent, scrim + accent reserved for specific overlays) and EXTENDS it with the ChatBox chrome. The inspector surface inherits wp-admin colors and is not re-tokenized.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `transparent` / inherit host page background | Avatar canvas mount point AND the ChatBox container both sit on whatever the WordPress theme already paints. Neither imposes an opaque page-level background. (Same deliberate-embed departure from typical 60/30/10 app chrome as Phase 8.) |
| Secondary (30%) | `#1e1e1e` at 55% opacity (`rgba(30,30,30,0.55)`) for overlays; ChatBox surfaces use `rgba(255,255,255,0.92)` (light) / `rgba(30,30,30,0.92)` (dark) — chosen by `prefers-color-scheme` | Overlay scrim (carried from Phase 8) behind "Click to talk"/connecting/error states. ChatBox card background is a translucent panel so it reads over arbitrary theme backgrounds — the two-surface (light/dark) split by media query keeps bubble text legible on both light and dark themes. The editor-preview banner uses the same translucent panel. |
| Accent (10%) | `#2271b1` (WP core admin blue, carried from Phase 8) | Reserved for EXACTLY: (1) the "Click to talk" button background (idle), (2) the ChatBox send-button background, (3) the **user** message-bubble background (user = the accent side; assistant = the neutral side — this asymmetry is the single strongest visual signal of speaker turn, mirroring khavee-app's `ChatBox.tsx` user-vs-assistant bubble styling), (4) the admin notice "Go to Settings" link. Nowhere else. |
| Destructive | `#d63638` (WP core error red) | Reserved for: the "Remove" button on a set background image (inspector, Part A — returns background to color mode); "Remove" on the avatar picker if a per-block avatar override exists. Both are admin-side-only; visitors never see destructive red. Never applied to the ChatBox, never to the avatar canvas, never to the editor preview. |

Accent reserved-for (explicit list, do not expand): "Click to talk" button bg, ChatBox send button bg, user message bubble bg, admin "Go to Settings" link. Not used for: borders, scrollbars, focus rings (those use wp-admin's own focus color in the inspector; the ChatBox focus ring uses a 2px solid `#2271b1` outline ONLY on the text input — that's the one allowed extension of the accent, since input focus is a sub-case of "ChatBox affordance").

**Inspector color caveat:** `ColorPalette` (Part A Background panel) and `RangeControl` sliders render with WP core's own component colors. The `#2271b1` accent token does NOT drive those — the color *value the user picks* for the background is a free-form hex stored in the config, independent of this contract's accent token.

### Conversation / message copy

The ChatBox renders whatever transcript comes back from the realtime session — this contract does NOT script sample conversation text. ## Interaction States (Phase-Specific Contract)

This phase's interaction surface is meaningfully larger than Phase 8's (it adds a live editor preview, a chat UI, and config-driven visual reactivity). Each row maps to a STUDIO-0X success criterion.

### Editor-side (Part B preview + Part A inspector)

| State | Trigger | Visual | Network/Permission Activity |
|-------|---------|--------|------------------------------|
| Preview — model loading | Block selected, avatar URL set, VRM still loading | Editor-preview banner over a `min-height` 32px reserved box; optional faint progress shimmer (CSS-only, no library) | VRM/GLB fetched from the WP Media Library URL; ZERO realtime/token calls |
| Preview — idle (loaded) | VRM loaded | Live 3D avatar in idle pose (SDK `VRMAvatar` with `idle` animation), framed by the selected Camera preset, lit by the Lighting intensity, on the Background color/image, scaled + offset per Avatar panel, inside the Layout width/height; ChatBox (if Show=on) rendered beside/below in its disconnected state. WYSIWYG-reactive: dragging any inspector slider re-renders the canvas within one frame. | None — no mic, no token, ever (hard EMBED-05 extension; the preview-mode bundle entry must not even import `OpenAIRealtimeProvider`) |
| Preview — Preview talking ON (Part D) | Author toggles "Preview talking" | Mouth/phoneme animation loops on the avatar (driven by `setMultipleExpressions` on a setInterval cycling the five mouth shapes `aa/ih/ou/ee/oh` at ~4Hz, no audio). A small "Preview talking" pill label appears overlaid in the preview corner so the author knows the motion is a demo, not a live session. | None |
| Preview — no avatar set | No global default avatar AND no per-block avatar | Editor-preview empty state (see Copywriting) with "Go to Settings" link | None |
| Preview — config reactivity lag | Author drags a slider faster than the VRM can re-render | Last-applied value wins; no spinner; the canvas simply catches up on the next frame. No debouncing of slider input beyond what R3F's frame loop already provides. | None |

### Published-side (Parts C + D, live SPA)

| State | Trigger | Visual | Network/Permission Activity |
|-------|---------|--------|------------------------------|
| Idle (carried from Phase 8) | Page load, configured + visitor has no special role | Avatar in idle pose, framed/lit/scaled per the merged config; "Click to talk" overlay; ChatBox (if shown) in disconnected state | None |
| Connecting (carried from Phase 8) | Visitor clicks "Click to talk" | Scrim + "Connecting…"; ChatBox switches from disconnected-text to empty-transcript state | Mic prompt + REST token mint fire now |
| Active — speaking (Part D live lip-sync) | Realtime session connected, assistant is speaking | Avatar mouth animates from the TTS-audio analyser via `useRealtime()`'s existing lip-sync path (`RealtimeAudioAnalyzer` → `setMultipleExpressions` → `VRMAvatar`); ChatBox shows the streaming assistant message | Live WebRTC |
| Active — listening / thinking | chatStatus transitions | Avatar expression/animation per `VRMAvatar`'s existing `chatStatus` handling; ChatBox input remains enabled | Live WebRTC |
| ChatBox — send text (Part C) | Visitor types + presses Enter (or clicks send) | User message bubble appears immediately (accent bg, right-aligned); assistant reply streams in as it arrives (neutral bg, left-aligned); transcript auto-scrolls to bottom on new message | `sendMessage(text)` on the same realtime provider — text input shares the session with voice, it does NOT open a second connection |
| ChatBox — scrollback | Transcript exceeds the visible region | Vertical scroll within the ChatBox body; auto-scroll-to-bottom on new message IF the visitor is already near the bottom (if they've scrolled up to read history, do NOT yank them down — standard chat-UX pinned-to-bottom rule) | None |
| ChatBox — shift+Enter | Visitor presses Shift+Enter in the input | Inserts a newline (multi-line input grows up to a max of ~5 lines, then scrolls internally); plain Enter sends | None |
| Config-not-applied fallback | A visual config key arrives blank/invalid from `data-khaveeai-config` | Fall back to the Phase 8 hardcoded scene defaults (ambient 1, directional 2.5, camera `[0,0,5]` fov 50) silently — never render a broken scene | None |
| Runtime connect error (carried) | `connect()` rejects | "Couldn't connect. [Try again]" in place of "Click to talk" | None until retry |

### Mutual-exclusivity + disable rules (Part A inspector)

| Rule | Behavior |
|------|----------|
| Background transparent ON | Color picker + Image picker both become disabled (greyed, not hidden) — matches CONTEXT.md "transparent-background toggle disables the color/image fields" |
| Background type = Color | Image picker disabled (greyed) |
| Background type = Image | Color picker disabled (greyed) |

| No avatar set | Camera, Lighting, Avatar scale/offset controls still enabled (they affect scene framing/lighting regardless), but the preview shows the "no avatar" empty state |

## Config Transport (STUDIO-05 — for the executor, locked by CONTEXT.md)

All new keys flow through the EXISTING `data-khaveeai-config` JSON contract — no new transport, no new endpoint, no `khavee-app` dependency. Specifically:

1. New `block.json` attributes (defaults = blank) →
2. `AvatarBlock::render_callback()` already merges block atts over `wp_parse_args( $atts, $defaults )` → extend the `$renderer_atts` array filter + `AvatarRenderer::public_safe()` whitelist →
3. Escaped JSON in `data-khaveeai-config` on the mount-point `<div>` →
4. `packages/wp-bundle/src/index.ts` parses it (already does for voice/instructions/avatarUrl/model/restUrl) →
5. Preview-mode entry and live entry both consume the same config object.

`KhaveeAvatarConfig` interface in `mount.tsx` gains the new optional fields; blank/absent values fall back to the Phase-8 hardcoded defaults so existing shortcodes/blocks render identically until an author sets a value.
