<decisions>
- **`contain` changes the plane size, not the texture crop.** Under `cover` the plane fills the
  camera frustum exactly and the texture is centre-cropped. Under `contain` the texture is
  uncropped (`repeat [1,1]`, `offset [0,0]`) and the *plane* shrinks to the largest rect of the
  image's aspect that fits inside the frustum rect. The alternative — keeping a frustum-sized plane
  and letterboxing via `repeat > 1` — is wrong under `ClampToEdgeWrapping`, which stretches the
  edge pixel across the letterbox instead of leaving it empty.
- **Only the `upper-region` derivation graduates.** `mean`, `saturation-weighted` and `dominant`
  were comparison scaffolding in spike 007. `mean` reproduces the MTOON-03 grey-rim defect and
  `dominant` picks the wrong half of a sky/ground photo; neither has a shipping use. The exported
  function therefore takes no strategy argument — there is no second strategy to select.
- **`deriveRimColor` returns `null`, not black, when no sufficiently-opaque pixel exists.** The
  caller (plan 16-04) must fall back to the rig's static default rim colour. Returning `{0,0,0}`
  would silently ship a black rim light, which is a visible defect that looks like "the rim feature
  did not work" rather than "no colour could be derived".
- **The 128px sampling ceiling is a caller concern, but the adversarial test is written at 128px.**
  Plan 16-04's canvas readback downsamples to at most 128px on the long edge (a bounded-work
  mitigation, see that plan's threat register). The fixtures here are therefore built at 128×128 so
  the assertions hold at the resolution the shipping path actually derives from, not at a
  resolution the shipping path never sees.
</decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied pixel buffer → `deriveRimColor` | Pixel data ultimately originates from a customer-supplied background image (decoded in plan 16-04). This module is the first code that iterates it. |
| caller-supplied numbers → `backdropLayout` | Camera/viewport/image dimensions reach this module from live DOM and texture state and can be zero, negative or non-finite mid-layout. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-01 | Denial of Service | `deriveRimColor` pixel loop | mitigate | The function is O(width × height) with no allocation per pixel, and the spike's `Array.prototype.slice.call` copy of the buffer is removed in favour of an in-place index bound. The size ceiling itself is enforced by the caller (plan 16-04 downsamples to ≤128px before readback); this module documents that expectation in its header so a future caller does not hand it a 8000×6000 buffer unknowingly. |
| T-16-02 | Tampering | `backdropLayout` degenerate inputs | mitigate | Non-finite/non-positive `fovDegrees`, `cameraAspect`, `distance` and `imageAspect` are guarded to a no-crop, finite layout. Without this a NaN propagates into `mesh.scale`, which three.js renders as an invisible mesh with no error — a silent failure, not a loud one. Asserted by test. |
| T-16-03 | Information Disclosure | derived rim colour | accept | The derived colour is a 3-channel average of a customer's own background image, rendered back into that customer's own scene. It crosses no trust boundary it did not already originate from and is not persisted or transmitted. |
| T-16-SC | Tampering | npm/pnpm installs | accept | No new dependencies. Both modules import nothing outside the TypeScript standard library; `vitest` is already a devDependency of `@khaveeai/react`. |
