<decisions>
- **`lighting` is a new optional prop; `autoLighting` stays `boolean`.** Locked by D-02. A consumer
  passing `lighting` while leaving `autoLighting` at its default `true` gets the configured rig; a
  consumer passing `autoLighting={false}` gets no rig at all and `lighting` is inert. That
  combination is documented, not made an error, because `autoLighting={false}` is what khavee-app
  ships today and turning it into a warning would be noise on a config that is still valid.
- **Each axis accepts `number | LightSpec`.** D-02's own example is `lighting={{ ambient: 0.6,
  key: 1.2, rim: 0.8 }}` — plain numbers — and CLAUDE.md calls for a beginner-usable API with no
  extra schema library. A bare number means intensity. `LightSpec` exists so colour and position
  are reachable without a second prop. Normalisation is one small internal helper.
- **D-04 is satisfied structurally, not by convention.** Because every axis and every shadow field
  falls back to `DEFAULT_LIGHT_RIG` when omitted, `lighting={{ ambient: someCustomerSetting }}`
  keeps the tuned shadow map, the fill and the rim by construction. This is the exact call
  khavee-app needs to keep its customer-facing `ambientLightIntensity` control wired, and it is
  asserted by a JSDoc `@example` on the prop so the adopting repo has a copy-paste target.
- **The rig's default values are spike 005's prototype values, and they are a floor.** ambient 0.32,
  key 1.35 `#fff4e6` at `[2,4,3]`, fill 0.45 `#cfe0ff` at `[-3,1.5,2]`, rim 1.6 `#bcd4ff` at
  `[-1.5,3,-4]`. Spike 005 said in as many words that these read but are weaker than a headline
  feature should be. Plan 16-06's human measurement checkpoint is where they get tuned up; shipping
  the measured prototype rather than an invented "improved" set keeps the D-11 comparison honest.
- **The rim's default colour is static `#bcd4ff`.** Research Open Question 1, resolved as option
  (a): one shared rig, upgraded for both components, with a documented static cool-white rim when
  no background-derived colour is available. `GLBAvatar` therefore gets the three-point rig with a
  static rim — consistent with D-12 and with D-03's "the rig was already on by default; only its
  contents change". The alternative (forking the rig so `GLBAvatar` keeps the old one) was rejected
  because D-12 explicitly puts both components on the new rig.
- **Ambient drops from 0.6 to 0.32 for every consumer on the default `autoLighting`.** That is the
  point — ambient is flat fill and is what eats the contrast Phase 15 traded away. It is a
  downstream-visible change and must be called out in the SUMMARY the same way Phase 15 called out
  the Cineon default. The escape hatch is `lighting={{ ambient: 0.6 }}`.
- **`AvatarContactShadows`, not `ContactShadows`.** Prefixed to match `AvatarLightRig` /
  `AvatarPostFX` and to avoid colliding with drei's own export in a consumer's import list.
  `ShadowFloor` is not touched, not deprecated and not given a mode flag (D-09).
- **`frames` defaults to `Infinity` and is exposed as the documented cost lever.** VRM avatars are
  always subtly animating (breathing, spring bones), so a finite default would produce a visibly
  stale shadow. RESEARCH Pitfall 3's continuous cost is therefore accepted and made explicit in the
  prop's JSDoc rather than hidden behind a default that looks free.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer app → `lighting` prop | Arbitrary caller-supplied numbers and colour strings reach three.js light constructors and shadow-map allocation. |
| SDK → app-owned `<Canvas>` scene graph | The rig is mounted inside the avatar's group but its lights illuminate the entire scene, including meshes the consumer owns. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-04 | Denial of Service | `lighting.shadow.mapSize` | mitigate | `mapSize` is fed straight to `shadow-mapSize`, and a caller-supplied 16384 allocates a 1 GB depth texture (or fails GPU allocation and blanks the canvas). Clamp the resolved value to the range 256–4096 in `resolveLight`'s shadow branch and document the clamp in the prop's JSDoc. An out-of-range request is clamped, not thrown — a lighting option is not worth crashing a consumer's scene over. |
| T-16-05 | Denial of Service | `AvatarContactShadows.resolution` and `frames` | mitigate | `resolution` is a render-target dimension with the same allocation profile; clamp to 128–2048. `frames` is documented as the continuous-cost lever (RESEARCH Pitfall 3) so the default is an examined choice rather than an unnoticed per-frame full-scene depth render. |
| T-16-06 | Tampering | rig lights affecting consumer-owned meshes | accept | `AvatarLightRig` mounts `directionalLight`s inside the avatar's group, but three.js lighting is scene-global — a consumer's own meshes are lit by this rig. This is pre-existing behaviour of the shipped rig, not introduced here, and `autoLighting={false}` is the documented opt-out. Recorded because the rig now adds two more lights, which makes the existing effect larger. |
| T-16-07 | Spoofing | `lighting.*.color` string | accept | Colour strings are handed to three.js's `Color` parser, which ignores anything it cannot parse and leaves the light white. No injection surface — the value never reaches DOM, CSS or a shader source string. |
| T-16-SC | Tampering | npm/pnpm installs | accept | No new dependencies. `@react-three/drei` ^10.7.6 is already a declared dependency of `@khaveeai/react` and already used elsewhere in the package. |
</threat_model>
