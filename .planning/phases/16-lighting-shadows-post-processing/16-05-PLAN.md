packages/react/src/utils/mtoonOutlines.ts

  export interface OutlineCounts {
    /** Surface MToon materials under `root`, excluding three-vrm's generated outline clones. */
    total: number;
    /** Of those, how many carry an authored outline (mode !== "none" and width > 0). */
    outlined: number;
  }
  export function countOutlinedMaterials(root: THREE.Object3D): OutlineCounts;

  /** Hide or restore authored outlines at runtime. Returns how many materials were touched. */
  export function setMToonOutlines(root: THREE.Object3D, enabled: boolean): number;

Verified upstream facts (read from `@pixiv/three-vrm@3.4.2` source — do not re-verify):
  - `MToonMaterial` is exported from `@pixiv/three-vrm` and usable with `instanceof`, the pattern
    `mtoonRepair.ts` already uses in its `forEachMToon` helper.
  - `outlineWidthFactor` is a getter/setter over a shader uniform
    (`get/set outlineWidthFactor() { this.uniforms.outlineWidthFactor.value }`), so assigning it
    takes effect on the next frame with no shader recompile and no model reload.
  - `outlineWidthMode` is `"none" | "worldCoordinates" | "screenCoordinates"`.
  - `isOutline` is `true` on the cloned outline material three-vrm generates and `false` on the
    surface material.
  - Outline generation happens in `_MToonMaterialLoaderPlugin._generateOutline` during
    `VRMLoaderPlugin.load()`, gated by `_shouldGenerateOutline` on the asset's authored values.
    There is no runtime API to generate an outline that was never authored.
</interfaces>

<decisions>
- **Respect-existing-only. No injection pass.** D-10 revised. Forcing an outline onto a material the
  artist left without one means replicating three-vrm's private `_generateOutline` — cloning the
  material, flipping `side` to `BackSide`, calling `geometry.addGroup` twice and converting
  `mesh.material` to an array — against an internal shape with no semver contract, and it
  contradicts Phase 15's locked repair-not-override semantics. A model with no authored outlines
  gets no outline, and "default on" is a no-op for it. That consequence is accepted and documented.
- **"Default on" is implemented as "do not suppress", not as "enable".** With `outlines` at its
  default `true` the SDK performs no traversal and writes no material field at all — the authored
  outlines simply render, exactly as they do today. This matters: a default that mutates every
  material to the value it already had would be indistinguishable from an override pass at a glance,
  and would fight `materialPreset="off"`'s restore-to-authored guarantee.
- **The toggle is non-cumulative.** Per `.planning/spikes/CONVENTIONS.md`, an A/B toggle must restore
  from the authored snapshot, never from the previous frame's already-modified state. The authored
  `outlineWidthFactor` is captured in a module-level `WeakMap<MToonMaterial, number>` the first time a
  material is suppressed, and restore reads from that map. A `WeakMap` is used so a disposed model's
  materials are collectable.
- **Only `VRMAvatar` gets the prop.** MToon exists only on VRM assets; `GLBAvatar` renders plain
  glTF PBR and has no outline concept. Adding an inert prop there would be API noise.
- **The counts are asserted against real assets, not described in a comment.** 6/19 on `male.vrm` and
  0/21 on the control are the two numbers that make D-10's revision true rather than plausible. A
  test is the only thing that keeps them true after a three-vrm bump.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| customer-supplied `.vrm` asset → SDK material mutation | Outline width values originate from an artist-authored (and in khavee-app's case, customer-uploaded) glTF extension block and are read and written by SDK code. |
| SDK → caller-owned scene graph | `setMToonOutlines` mutates materials on a `THREE.Object3D` the consumer owns. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-19 | Tampering | mutation of caller-owned materials | mitigate | The toggle writes to materials the consumer owns. Mutation is confined to a single numeric uniform (`outlineWidthFactor`) on materials that already declare an outline, the authored value is snapshotted in a `WeakMap` before the first write, and restore reads from that snapshot rather than from current state — so the SDK can always hand the asset back in the condition it received it. Asserted by the non-cumulative test. |
| T-16-20 | Denial of Service | authored `outlineWidthFactor` from an untrusted asset | accept | A hostile `.vrm` could author an enormous outline width, producing a full-screen back-face smear and a GPU cost. This is out of this plan's reach: the value is applied by `@pixiv/three-vrm`'s loader at parse time, before any SDK code sees the material, and clamping it would be exactly the override-the-artist behaviour D-10 rules out. Asset-level validation belongs to khavee-app's upload path, not to a render-quality toggle. Recorded rather than silently ignored. |
| T-16-21 | Denial of Service | test-time parsing of real `.vrm` assets | mitigate | The asset test parses two multi-megabyte GLB files. Bounded by a per-test `{ timeout: 120_000 }` and by loading each model once per `it` block, mirroring `mtoonRepair.assets.test.ts`. Model filenames are hardcoded literals resolved from `import.meta.url`, never derived from input. |
| T-16-22 | Denial of Service | unmeasured per-frame outline cost | mitigate | D-10 accepted an unquantified draw-call cost. Research reduced the estimate from ~19 extra draw calls to ~6 on `male.vrm` and 0 on assets with none authored, but the frame-time cost is still unmeasured. Plan 16-06 carries a human measurement checkpoint in a visible focused tab; browser automation is explicitly excluded (spikes 004/005 produced confident false readings). |
| T-16-SC | Tampering | npm/pnpm installs | accept | No new dependencies. `three`, `@pixiv/three-vrm` and `vitest` are already present in `@khaveeai/react`. |
</threat_model>
