# Phase 16: Lighting, Shadows & Post-Processing - Research

**Researched:** 2026-09-14
**Domain:** react-three-fiber lighting/shadow/post-processing composition on top of MToon-shaded VRM avatars
**Confidence:** MEDIUM-HIGH (all four research areas verified directly against installed package source under `node_modules/.pnpm`, not training knowledge; the two prescriptive/tunable areas — rig values and grading defaults — are necessarily MEDIUM since they are aesthetic judgment calls, not facts)

## Summary

All four un-researched areas turned out to have concrete, checkable answers in the installed
package source, and two of them surface findings that materially change what CONTEXT's decisions
can mean in practice.

`ContactShadows` (drei 10.7.6) and `ShadowFloor` are mechanically opposite: `ShadowFloor` is
almost free because it reuses the shadow map the main render pass already computes for
`AvatarLightRig`'s directional light; `ContactShadows` does its own extra full-scene depth render
plus two (or three, if `smooth`) blur passes **every frame by default**, and needs no light at
all — it is a `MeshDepthMaterial` render-to-texture trick, not real shadow mapping. They are
complementary, not redundant, confirming D-09's "keep both" instinct, but `ContactShadows`'s
default cost model (`frames={Infinity}`) needs an explicit throttling recommendation.

MToon outlines are generated by `@pixiv/three-vrm`'s own loader plugin **at glTF-parse time**,
gated on the asset's own authored `outlineWidthMode`/`outlineWidthFactor` — not by anything the
SDK controls today. Real-asset data (spike 001's audit) shows this is highly asset-dependent:
`male.vrm` has outlines pre-generated on only 6 of 19 materials (not all 19, contradicting the
ROADMAP's "19 -> 38 draw calls" estimate), and the "well-authored" control asset
`3636451243928341470.vrm` has **zero** materials with outlines authored at all. D-10's "ship
outlines default ON" therefore cannot mean "every model gets an outline" without the SDK building
its own post-load injection pass mirroring three-vrm's private `_generateOutline` method — this is
buildable (all the primitives are public) but is real, undocumented scope, not a one-line default
flip.

The post-processing area surfaced the single highest-value finding in this research:
`@react-three/postprocessing@3.0.4`'s `<EffectComposer>` **unconditionally forces
`gl.toneMapping = THREE.NoToneMapping`** for as long as it is mounted, restoring the prior value
only on unmount — regardless of which effects are inside it. `NoToneMapping` is the option spike
003 explicitly refuted as a saturation-destroying "flat look". Because `AvatarPostFX` already
mounts an `EffectComposer` whenever either `bloom` or `smaa` is true (both default `true`), **every
current production consumer of `AvatarPostFX`, including khavee-app's own `<AvatarPostFX
bloom={false} />`, is already rendering under `NoToneMapping` today**, silently overriding
whatever `VRMAvatar`/`GLBAvatar` set via `applyRendererDefaults`. This is a pre-existing landmine,
not something Phase 16 introduces, but Phase 16 is the phase that must fix it, because it is
exactly when the composite chain grows (DOF, vignette, grading) and when "must not silently undo
Phase 15's tone curve" becomes an explicit requirement. The fix is well-supported: `postprocessing`
6.37.8 (the version resolved under `@react-three/postprocessing@3.0.4`) ships
`ToneMappingMode.CINEON` as a first-class composite-chain effect, so appending
`<ToneMapping mode={ToneMappingMode.CINEON} />` as the last effect in the chain restores the
intended curve inside the composite pipeline itself.

**Primary recommendation:** Ship the three-point rig as an upgrade to the existing
`AvatarLightRig` (shared by both avatar components), add `ContactShadows` as a genuinely separate
opt-in component per D-09 with `frames` exposed and documented as a cost lever, treat outlines as
"respect what three-vrm already generated" for v1 (do not promise outlines on every model), and
make `AvatarPostFX`'s effect chain always end with a `ToneMapping` pass matching the caller's
renderer-level curve so DOF/vignette/grading cannot silently regress Phase 15's saturation work.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Three-point light rig (key/fill/rim) | Browser / Client (R3F scene graph) | — | Pure three.js scene-graph state inside the avatar's own group; no server involvement |

| MToon outline generation | Browser / Client (glTF-load-time, inside `@pixiv/three-vrm`'s loader plugin) | — | Happens during `VRMLoaderPlugin.load()`, entirely client-side; no build-time or server-time step exists to pre-bake this |

No capability in this phase has a server/API tier; the whole phase is client-side WebGL/R3F work,
consistent with the rest of `packages/react`.

## Project Constraints (from CLAUDE.md)

- **Compatibility:** The existing `openai-stt-tts` provider and every current `VRMAvatar`/
  `GLBAvatar` consumer must keep working unchanged. Any change to `AvatarLightRig`'s exported
  shape (e.g. adding required props) would break `GLBAvatar`'s existing zero-arg
  `<AvatarLightRig />` call — new params must be optional with defaults matching current visual
  intent as closely as the rig redesign allows.
- **Vendor neutrality:** Public API surface must not leak vendor-specific types. Precedent already
  set in `mtoonRepair.ts` (`MToonDebugMode` is a local string union, not a re-exported
  `@pixiv/three-vrm` enum) — the same pattern applies to any new outline-mode or tone-mapping-mode
  prop shape this phase introduces (e.g. do not re-export `postprocessing`'s `ToneMappingMode` enum
  directly from `@khaveeai/react`'s public surface; mirror it as a local union like
  `MToonDebugMode` does).
- **Code style / conventions:** New optional props (`lighting`, `backgroundFit`, outline toggles)
  follow the established pattern — JSDoc `/** ... */` with `@default` documented inline, optional
  (`?`) fields, `camelCase`, section-divider comments (`// ── Section Name ──`) for new logical
  blocks inside `renderQuality.tsx`.
- **Error handling:** No new async lifecycle is introduced by this phase (lighting/shadows/postFX
  are synchronous render-state), so the `try/catch` + `onError` normalization pattern used by
  `OpenAISTTTTSProvider` does not directly apply here — but any background-image decode (for rim
  derivation / backdrop texture) is async and should follow the codebase's `error instanceof Error
  ? error : new Error(String(error))` normalization if it can fail (e.g. CORS-blocked image load).
- **Renderer-wide mutation is accepted but must be documented:** `applyRendererDefaults` already
  mutates the Canvas-shared `WebGLRenderer`. Any new renderer-level change (e.g. forcing tone
  mapping back after `EffectComposer` mounts) inherits this documented precedent and must be
  commented the same way.

### Pattern 1: Subject-tracked Depth of Field

**What:** Feed `DepthOfField`'s `worldFocusDistance` from a per-frame measurement of
`camera.position.distanceTo(subjectPosition)` rather than a constant.
**When to use:** Any time DOF is enabled and the camera can move (orbit controls today; Phase 17's
state-driven reframing later) — i.e., always, per spike 004's validated finding.
**Example:**
```tsx
// Source: apps/playground/src/app/lighting-spike/page.tsx (SubjectTracker component,
// spike 004, VALIDATED) — graduate this pattern, not necessarily the exact component.
useFrame(({ camera }) => {
  const distance = camera.position.distanceTo(subjectRef.current.position);
  if (Math.abs(distance - lastDistance.current) > 0.02) {
    setFocusDistance(distance); // only pushes state when it actually moved
    lastDistance.current = distance;
  }
});
```

### Pattern 2: Composite-chain tone mapping restoration

**What:** Any `EffectComposer`-based chain must end with `<ToneMapping mode={...} />` matching the
renderer-level curve the avatar component otherwise sets via `applyRendererDefaults`.
**When to use:** Always, whenever `AvatarPostFX` (or any future post-processing surface) is
mounted — not just when DOF/vignette/grading are added. This is a **retroactive fix**, not new
scope: `AvatarPostFX`'s existing Bloom/SMAA chain already has this bug today.
**Example:**
```tsx
// Source: @react-three/postprocessing 3.0.4 dist/index.js — EffectComposer wrapper
// unconditionally does:
//   useEffect(() => {
//     const prior = gl.toneMapping;
//     gl.toneMapping = THREE.NoToneMapping;
//     return () => { gl.toneMapping = prior; };
//   }, [gl]);
// verified directly in node_modules/.pnpm/@react-three+postprocessing@3.0.4.../dist/index.js
import { ToneMapping } from "@react-three/postprocessing";
import { ToneMappingMode } from "postprocessing"; // transitive dep, see Standard Stack note

<EffectComposer>
  {/* ...DepthOfField, Vignette, HueSaturation, Bloom, SMAA... */}
  <ToneMapping mode={ToneMappingMode.CINEON} />
</EffectComposer>
```

**What:** Sample only the top third of the background image/colour, weighting each pixel's
contribution by its own HSV saturation, rather than a plain mean or histogram mode.
**When to use:** Whenever `lighting.rim` derives its colour from a `backgroundValue`/
`backgroundImageUrl` source (D-05).

For a flat `COLOR` background, all four derivations agree trivially (spike 007) — no branch is
needed for the `COLOR` case beyond "use the colour directly, skip sampling".

### Anti-Patterns to Avoid
- **Assuming a constant `worldFocusDistance` is "good enough" because the demo camera is static
  today.** Spike 004 proved this fails the moment `OrbitControls` scrolls, and Phase 17 will add
  camera moves by design (ROADMAP). Ship subject-tracking from day one.
- **Reusing `averageTextureColor` (or any plain mean) for rim-from-background.** Spike 007 proved
  this reproduces the exact grey-rim defect MTOON-03 already fixed once, one level up (background
  photo instead of base texture).
- **Assuming `outlineWidthMode="none"` on an asset means "outlines are disabled and can be turned
  on with a boolean prop."** It means three-vrm's loader plugin never ran `_generateOutline` for
  that mesh — there is no outline material/geometry-group to toggle. Turning outlines "on" for
  such an asset requires building a new post-load injection pass (see Pitfall 2), not a flag flip.
- **Mounting `AvatarPostFX` and assuming the renderer's `toneMapping` prop is still in effect.**
  `EffectComposer` overrides it for the Canvas's whole lifetime while mounted (Pitfall 1).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Soft ground-contact shadow blob | A custom render-to-texture + blur pipeline | drei's `ContactShadows` | Exact mechanism (two-pass `HorizontalBlurShader`/`VerticalBlurShader` over a `MeshDepthMaterial` render) is already implemented, tested, and maintained upstream; hand-rolling it duplicates ~110 lines of render-target/blur-pass plumbing already in `node_modules` |
| DOF bokeh | A custom shader pass | `postprocessing`'s `DepthOfFieldEffect` via `@react-three/postprocessing`'s `<DepthOfField>` | Real depth-of-field with autofocus/target support is a substantial shader (circle-of-confusion computation, bokeh disc blur) already spike-validated (004) against this exact scene |
| Colour grading (hue/saturation/brightness/contrast) | Custom fragment shader uniforms bolted onto MToon | `HueSaturationEffect` / `BrightnessContrastEffect` from `postprocessing` | Standard, composable, already ordered correctly relative to tone mapping when the trailing `ToneMapping` pass pattern (above) is followed |
| Vignette | A radial-gradient overlay mesh or custom shader | `VignetteEffect` (`technique`, `offset`, `darkness` props already cover the standard "default" and "eskil" falloff curves) | Same effect-ordering benefits as above; a hand-rolled overlay mesh would need its own tone-mapping/blend-mode reasoning that `postprocessing` already solved |

**Key insight:** Every one of this phase's four post-processing asks (DOF, vignette, hue/sat,
brightness/contrast) is a named, exported effect in the exact `postprocessing` version already
installed. The only genuinely unbuilt piece is MToon outline injection for assets that did not
author outline data — everything else is composition of existing library primitives.

## Common Pitfalls

### RESEARCH Pitfall 1: `EffectComposer` silently forces `NoToneMapping` while mounted
**What goes wrong:** Any avatar rendered inside a Canvas that also mounts `AvatarPostFX` (bloom or
smaa true — both default true) renders under `THREE.NoToneMapping`, not whatever
`applyRendererDefaults` set (`CineonToneMapping` for `VRMAvatar`, `ACESFilmicToneMapping` for
`GLBAvatar`), for as long as the `EffectComposer` component is mounted.
**Why it happens:** `@react-three/postprocessing@3.0.4`'s internal `EffectComposer` wrapper
(`apps/playground/node_modules/@react-three/postprocessing/dist/index.js`) runs
`useEffect(() => { const prior = gl.toneMapping; gl.toneMapping = THREE.NoToneMapping; return () =>
{ gl.toneMapping = prior; }; }, [gl])` unconditionally — this is because `postprocessing`'s
multi-pass render targets need linear (untone-mapped) intermediate buffers; tone mapping is meant
to be reapplied as one of the composite passes, not left at the renderer level.
**How to avoid:** Always end the `AvatarPostFX` effect chain with `<ToneMapping mode={...} />`
(from `@react-three/postprocessing`, backed by `postprocessing`'s `ToneMappingEffect`), matching
whichever curve the avatar component would otherwise set at the renderer level. `ToneMappingMode`
includes `CINEON` (verified in `postprocessing@6.37.8`'s type declarations), so Phase 15's exact
choice can be reproduced inside the chain.
**Warning signs:** Any visual A/B where "avatar looks flatter/less saturated whenever
bloom/postFX/SMAA is turned on" — that symptom is this bug, not a rig or material problem. This
almost certainly already explains part of why production (which mounts `<AvatarPostFX
bloom={false} />`, leaving `smaa` at its default `true`) looks less vivid than the
`mtoon-spike`/`lighting-spike` pages that do not mount `AvatarPostFX` at all.

### RESEARCH Pitfall 2: MToon outlines are baked in at load time, not toggleable for every asset
**What goes wrong:** A boolean `outlines` prop that simply forces something "on" cannot make
outlines appear on a model whose glTF `VRMC_materials_mtoon` extension data has
`outlineWidthMode: "none"` for a given material, because three-vrm's `_generateOutline` (invoked
from `_setupPrimitive` during `VRMLoaderPlugin.load()`) never converted that mesh's material into
a `[surface, outline]` array or added the second `geometry.addGroup` needed to render the
back-face outline pass. There is no `outlines={true}` runtime lever for that mesh — the mesh
literally has no outline draw call to enable.
**Why it happens:** Outline generation is gated in `_shouldGenerateOutline` (three-vrm 3.4.2,
`lib/three-vrm.module.js`) on the material's *authored* `outlineWidthMode !== "none" &&
outlineWidthFactor > 0`, checked once, at parse time — not re-evaluated per frame or exposed as a
public "regenerate outlines" API.
**How to avoid:** For v1, scope D-10 as "do not suppress outlines the asset already declares" (a
real, small, safe default-on: expose `outlineWidthFactor = 0` toggling on materials that already
carry a cloned `isOutline` material, since `outlineWidthFactor` is a direct uniform getter/setter
on `MToonMaterial` — `material.outlineWidthFactor = 0` hides an existing outline instantly, no
reload, confirmed in source). Treat "force outlines onto assets with no authored outline data" as
separate, larger scope requiring a custom injection pass that replicates `_generateOutline`
(clone material, `side = THREE.BackSide`, `geometry.addGroup(...)` twice, convert
`mesh.material` to an array) — call this out explicitly to the planner rather than assuming it is
included in "default ON".
**Warning signs:** Testing outlines only against `male.vrm` (6/19 materials have them
pre-authored) will look like partial success; testing against `3636451243928341470.vrm` (the
Phase 15 "well-authored, should render unchanged" control asset, 0/21 materials with authored
outlines) will show **no outline appears at all**, regardless of any prop value, unless the
injection pass is built. Verified directly against `.planning/spikes/001-mtoon-runtime-audit/audit-result.json`:

| Asset | Total materials | Materials with `outlineMode !== "none"` |
|---|---|---|
| `male.vrm` | 19 | 6 |
| `3636451243928341470.vrm` | 21 | 0 |
| `262410318834873893.vrm` | 18 | 10 |
| `amongus.vrm` | 2 | 0 |

This directly contradicts the ROADMAP's cost estimate ("19 materials on `male.vrm`, so roughly
19 -> 38 draw calls") — the real number for `male.vrm` today is 6 extra draw calls if only
respecting authored outlines, or up to 19 extra if a new injection pass forces outlines onto every
material. **Spike 006 (outline-draw-cost, PENDING) must measure against whichever of these two
scopes the plan actually chooses**, and should measure `male.vrm` (mixed) rather than only a
best-case or worst-case asset.

### RESEARCH Pitfall 3: `ContactShadows` re-renders the whole scene every frame by default
**What goes wrong:** `ContactShadows`'s default `frames = Infinity` means it performs one extra
full-scene depth render (`gl.render(scene, shadowCamera)` with `scene.overrideMaterial =
MeshDepthMaterial`) plus 2 blur passes (3 if `smooth={true}`, the default) on **every single
frame**, forever — a continuous, unthrottled cost on top of the main render pass, unrelated to
whether the avatar's pose is actually changing.
**Why it happens:** `ContactShadows` is a screen-space-independent, camera-agnostic render-to-
texture trick (top-down orthographic camera baked once per `useFrame` call by default) — it has
no built-in "only recompute if something moved" heuristic; that is what the `frames` prop is for,
and it defaults to "recompute forever."
**How to avoid:** Expose (or internally default to) a finite `frames` value when the avatar's pose
is not changing rapidly (e.g., during `idle`/`listening` chat states), or accept the continuous
cost and measure it explicitly via spike 006's methodology (visible, focused tab only — see
Pitfall 4). Since VRM avatars are essentially always subtly animating (breathing, spring bones),
`frames={Infinity}` may be unavoidable for a always-correct shadow, but this should be a stated,
measured tradeoff, not an unexamined default.
**Warning signs:** Frame-time regression that appears only when `ContactShadows` is mounted and
does not correlate with material or geometry complexity — check `frames` first.

### RESEARCH Pitfall 4 (carried forward from spikes 004/005, restated for Phase 16 planning):
Frame-time and pixel-readback numbers must never be gathered through browser automation — an
automated tab is `visibilityState: "hidden"`, throttling `requestAnimationFrame` to ~1Hz and
returning empty/null WebGL buffer reads. This applies directly to spike 006's outline cost
measurement and to any Phase 16 plan step that claims a specific FPS or draw-call number — those
numbers require a human running a visible, focused tab, exactly as spikes 004 and 005 already
proved and as this phase's own constraints reiterate.

```ts
  opacity?: number;   // default 1
  width?: number;     // default 1 (multiplied by `scale`)
  height?: number;    // default 1 (multiplied by `scale`)
  blur?: number;      // default 1 — Gaussian blur radius passed to Horizontal/VerticalBlurShader
  near?: number;      // default 0 — orthographic shadow camera near plane
  far?: number;       // default 10 — orthographic shadow camera far plane (how far above the
                       //   ground the camera samples depth from)
  smooth?: boolean;   // default true — runs a second, softer blur pass (extra cost)
  resolution?: number;// default 512 — render target resolution, both axes
  frames?: number;    // default Infinity — re-render every N frames; see Pitfall 3
  scale?: number | [x: number, y: number]; // default 10
  color?: THREE.ColorRepresentation;        // default '#000000'
  depthWrite?: boolean; // default false
};
```
No light is required — `ContactShadows` renders `scene.overrideMaterial = MeshDepthMaterial` into
its own `WebGLRenderTarget`, entirely independent of `AvatarLightRig`'s directional light.

## Open Questions

1. **Does the three-point rig apply to `GLBAvatar` too?**
   - What we know: `AvatarLightRig` is a single shared function (`packages/react/src/utils/renderQuality.tsx`) mounted identically by both `VRMAvatar` and `GLBAvatar` (`{autoLighting && <AvatarLightRig />}` in both, verified by grep). `GLBAvatar` deliberately stays on `ACESFilmicToneMapping` because it renders plain glTF PBR, not MToon (Phase 15 precedent, confirmed in `GLBAvatar.tsx`'s own tone-mapping comment).
   - What's unclear: CONTEXT explicitly scopes the new `lighting` prop (D-02) to `VRMAvatar` only (canonical_refs names `VRMAvatar.tsx` as "where the new lighting prop lands", not `GLBAvatar.tsx`). But since `AvatarLightRig` is the *same function*, upgrading its default light values also changes what `GLBAvatar`'s zero-arg `<AvatarLightRig />` call renders — a rim light with no colour-derivation input (since `GLBAvatar` has no background-compositing feature in scope) would render with some fallback rim colour on every current `GLBAvatar` consumer, silently.
   - Recommendation: Treat this as an explicit planning decision, per the must_address note. Two clean options: (a) ship the upgraded `AvatarLightRig` as the new shared default with a documented static fallback rim colour (e.g. neutral cool white) when no background-derived colour is available, so `GLBAvatar` gets the three-point rig with a static rim; or (b) fork the rig into `AvatarLightRig` (legacy, used by `GLBAvatar`) and a new `AvatarLightRig3Point`/parametrized variant (used by `VRMAvatar`), leaving `GLBAvatar` completely untouched. Option (a) is more consistent with "the rig was already on by default; only its contents change" (D-03) but must be stated as a deliberate choice in the plan, not left implicit.

2. **Exact numeric gate for D-11's contrast recovery.**
   - What we know: Spike 005 established the gate must be a same-harness delta (`three-point >= legacy`, same framing/materialPreset/session) — no absolute number is portable. Spike 005 explicitly withheld even its own measured numbers pending explanation of two anomalies (implausible `coveredPixels` and `valueSpread`).
   - What's unclear: Whether those two anomalies are measurement-harness bugs (most likely, per spike 005's own suspicion) or something about the `VRMAvatar`/`applyMeshRenderFlags` render path. Until resolved, no plan step can cite a specific expected number.
   - Recommendation: Wave 0 of the Phase 16 plan should include re-running spike 005's live-measurement panel (human, visible tab) with the anomalies specifically investigated (`coveredPixels` ~42% of frame with backdrop off — check whether canvas alpha/clear-color pixels are being counted as "covered"), before locking any rig tuning to a numeric target.

3. **Whether `postprocessing`'s `ToneMappingMode.CINEON` should be imported from the `postprocessing` package directly, or whether `@react-three/postprocessing` re-exports it.**
   - What we know: `@react-three/postprocessing@3.0.4`'s `dist/index.js` exports a `ToneMapping` *component* wrapping `ToneMappingEffect`, but grep of its export list did not show a re-exported `ToneMappingMode` enum — the enum lives in the `postprocessing` package's own type declarations (`node_modules/.pnpm/postprocessing@6.37.8.../build/types/index.d.ts`).
   - What's unclear: Whether importing directly from `postprocessing` (a transitive, undeclared dependency) is acceptable per this repo's dependency-declaration conventions, or whether it should be added as an explicit `peerDependency`/`dependency` of `packages/react`.
   - Recommendation: Add `postprocessing` as an explicit dependency of `packages/react` (matching the resolved 6.37.8) if `ToneMappingMode` needs to be imported by name; alternatively, hardcode the numeric enum value (`CINEON` is index 6 in the enum, verified above) to avoid the import, mirroring the `MToonDebugMode` local-union pattern the codebase already uses to avoid an undeclared-dependency import.
