# Procedural Delta Layer — Performance Budget Research

**Ticket:** khavee-ai/khavee-sdk#10 ("Research procedural delta layer performance budget")
**Context:** Locked decision (#2) commits to an always-on, per-frame procedural delta layer — small code-computed rotation/position/expression offsets applied every frame on top of whatever `AnimationMixer` clip is currently playing. This extends the existing shipped pattern in `packages/react/src/VRMAvatar.tsx` (ref-driven blinking, deliberately kept out of React state to avoid re-renders — see inline comment at `VRMAvatar.tsx:308-313`, quoted below). This document sizes the frame-time budget for that layer as more procedural systems stack in the same `useFrame` callback, and recommends techniques (with citations) for staying inside budget, including graceful degradation under pressure.

Existing codebase comment this research extends (`packages/react/src/VRMAvatar.tsx:308-313`):
> "Blinking system. blinkState is a ref, not React state: it's only ever read synchronously within the same useFrame callback that writes it, never rendered in JSX — calling a state setter here would re-render this component on every single animation frame during a blink (blink lasts ~7 frames at blinkAnimationRef's 0.15/frame step), fighting the R3F render loop for the main thread and producing visible stutter."

---

## 1. Stacking inventory

All systems below run inside the same `useFrame` callback, after `AnimationMixer.update(delta)` runs (or interleaved with it) and before/around `currentVrm.update(delta)`.

| # | System | Ticket | What it touches | Update cadence needed | Notes |
|---|--------|--------|------------------|------------------------|-------|
| 1 | **Blinking** | shipped | 2 expression blendshapes (`blinkLeft`, `blinkRight`) via `ExpressionManager.setValue()` | Every frame (only *active* ~7 frames per blink cycle; idle most of the time) | Already ref-driven, proven pattern. Cost is 2 `setValue()` calls + a `Math.sin()`, gated behind an `isBlinking` boolean so it's near-zero cost when not actively blinking. |
| 2 | **Breathing** | #3 | 1-2 bone quaternions (chest/spine) | Every frame — continuous sine cycle, randomized range/period | One `Math.sin()` + one quaternion write per affected bone (~1-2 bones). Composes with other spine-touching systems (see §4 composition guidance). |
| 3 | **Weight-shift sway** | #3 | 1-2 bone quaternions (hip/spine) | Every frame — independent randomized cycle from breathing | Same shape as breathing: cheap per-frame trig + quaternion write. Overlaps spine bone with breathing — composition order matters (§4). |
| 4 | **Expression rest-state drift** | #3, VRM-only | 1-2 expression blendshapes | Every frame, but *slow* drift (target values change over seconds) — a strong candidate for degraded update rate under pressure | Cheapest system numerically (same shape as blinking: `setValue()` calls), but least perceptually sensitive to being throttled since the drift itself is already slow-moving. |
| 5 | **Audio-reactive procedural amplitude** | #4 | Reads a scalar (already-computed live volume) from `useAudioLipSync`; writes to head/gesture bone quaternions or scales existing procedural outputs | Every frame while `chatStatus === "speaking"` | Does **not** add new signal-processing cost itself — it consumes output already computed by `useAudioLipSync`, a separately-shipped, comparatively heavy hook (MFCC/DTW phoneme detection via `meyda`, per `packages/react/src/hooks/useRealtime.ts`'s embedded `RealtimeAudioAnalyzer`). That hook's cost is out of scope for this ticket's budget (it's pre-existing and already shipped) but is worth noting as the actual heavy neighbor in the same frame — the procedural amplitude system itself is just a multiply against bone rotations already being computed by breathing/sway/gaze. |
| 6 | **Gaze/attention system** (future, not yet ticketed) | "fog" item | Likely head/neck/eye bone quaternions, possibly look-at target computation (vector math, not just sine) | Every frame while active; look-at target itself could update at reduced rate (target rarely needs 60Hz precision) | Not spec'd here. Sized only as a future addition: architecturally it lives in the same procedural layer and will be the first system whose *target computation* (a look-at solve) is more expensive than a sine wave — a natural first candidate for the degradation scheme in §5 if/when it's built. |

Aggregate shape: by full stack (systems 1-5), this is roughly **6-10 bone-quaternion writes** and **4-6 expression `setValue()` calls** per frame, each preceded by cheap scalar math (`Math.sin`, multiply, occasional `Math.random` for re-seeding cycle bounds — not per-frame). This is a small, bounded, enumerable set of operations, not an open-ended system — important context for §2's budget sizing.

## 2. Frame-budget finding

**Directly cited numbers:**

- Standard 60fps target gives a **16.66ms total frame budget** ("the browser has 16.66 milliseconds to produce each frame") — [web.dev, Rendering Performance](https://web.dev/articles/rendering-performance).
- The same source gives the practically-relevant sub-budget: **"all of your work needs to be completed inside 10 milliseconds"** per frame, because the browser reserves the remainder of the 16.66ms for its own rendering/compositing overhead — [web.dev, Rendering Performance](https://web.dev/articles/rendering-performance).
- React Three Fiber's own scaling-performance guidance confirms the same 60fps/16.6ms framing for three.js apps generally ("three.js apps usually run in a game-loop that executes 60 times a second") but **does not publish a specific procedural-logic-only sub-budget number** — [R3F docs, Scaling Performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance).
- Concrete evidence that `AnimationMixer.update()` + skeleton matrix propagation is the dominant *existing* CPU cost in this exact code path (VRM/skinned-mesh + mixer), from a three.js Discourse thread profiling 300 animated skinned meshes (25 bones each) on a mid-range laptop: frames started dropping below 60fps past ~200 concurrent skinned meshes, with profiling showing **`AnimationMixer.update()` (`PropertyMixer.apply()`, `Euler.setFromRotationMatrix()`), `updateMatrixWorld()` (7500 nested `Object3D`s = 300×25 bones), and `Skeleton.update()`** together accounting for roughly 75% of scene CPU time — [three.js Discourse, "Optimization of large amounts (100-1000) of Skinned Meshes"](https://discourse.threejs.org/t/optimization-of-large-amounts-100-1000-of-skinned-meshes-cpu-bottlenecks/58196). This is a many-avatar scene, not this SDK's single-avatar case, but it is the best available primary-source data point confirming that mixer/matrix-update cost is non-trivial and scales with bone count — i.e., it is the thing the procedural layer's budget has to share room with, on a *per-bone-count* basis similar to this SDK's ~55-bone VRM rig ([VRM 1.0 humanoid spec](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_vrm-1.0/humanoid.md): 55 possible humanoid bones, 15 required).
- No source found gives an authoritative, specific millisecond figure for "AnimationMixer.update() alone, for one avatar, N bones" or for "procedural logic budget specifically" — this is a genuine gap in available primary sources.

**My own synthesis (not a cited fact — flagged as reasoning, not authority):**

Given (a) the 10ms-of-JS-work guideline as the realistic ceiling before jank risk on a 60fps target, (b) that this SDK renders a *single* VRM avatar (not the 300-mesh stress case above), and (c) that React/R3F reconciliation, the mixer update, `vrm.update()`, and the WebGL render/draw-call submission all compete for the same 10ms:

- A **single avatar's** `AnimationMixer.update()` + `vrm.update()` pass, at ~55 bones, is very unlikely to be more than low-single-digit milliseconds on typical hardware (the 58196 Discourse case only became bottlenecked at 200+ *concurrent* meshes of similar bone count, i.e., ~5000+ bones total; one avatar is two orders of magnitude below that).
- That leaves a rough **order-of-magnitude budget of ~1-2ms** as a conservative target ceiling for the entire procedural delta layer (all 5-6 systems combined) on a single avatar, out of the ~10ms JS-work guideline, leaving headroom for React reconciliation, input handling, and the render/draw-call submission itself.
- This is a synthesized target, not a benchmarked one — the recommendation in §5 (measure `delta`/frame time at runtime and react to it) exists specifically because no static number can be trusted without in-app profiling on real target hardware, and this document does not have access to run that profiling.

## 3. Per-operation cost findings

- **Quaternion operations** (three.js `Quaternion.js` source, `multiply`, `slerp`, `setFromAxisAngle`): all operate **in-place** on the instance's internal `_x/_y/_z/_w` fields and **do not allocate** internally. `multiply` is a fixed ~16 multiply-add operations (quaternion Hamilton product); `setFromAxisAngle` is ~8 operations (1 division, 1 sin, 1 cos, 4 multiplies); `slerp` is the most expensive single call at roughly 25-30 floating-point operations (dot product, conditional trig branch, interpolation) — still trivially cheap in absolute terms (sub-microsecond) at the counts in §1 (6-10 bone writes/frame). [Source: three.js `Quaternion.js`, `mrdoob/three.js` repo.]
- **`VRMExpressionManager.setValue()`**: no benchmarking data or authoritative statement was found in `@pixiv/three-vrm`'s docs or GitHub discussions quantifying its per-call cost. Structurally (per the library's own architecture docs) it sets a normalized blend value that is applied to underlying morph targets / material properties during the VRM's `update()` pass, not immediately — so its direct cost is a value-store write; the actual blendshape application cost is folded into `vrm.update(delta)`, which this SDK already calls once per frame regardless of the procedural layer. No source quantifies this in ms. [Source: `@pixiv/three-vrm` docs, https://pixiv.github.io/three-vrm/docs/interfaces/three-vrm.VRMParameters.html and related pages — architecture description only, no perf numbers.]
- **Bone rotation writes** (`object.quaternion.set(...)` / `.copy(...)`): a raw field write, effectively free on its own. The real cost is downstream — `updateMatrixWorld()`, which recomposes the local matrix from position/quaternion/scale (`Matrix4.compose`) and propagates to children. This cost is **already paid once per frame** by the existing render loop (three.js updates world matrices for the scene graph regardless of whether the procedural layer runs), so the *incremental* cost the procedural layer adds is only the quaternion math itself (previous bullet), not a second matrix-update pass — writing to a bone's quaternion before the frame's regular `updateMatrixWorld()` call adds no extra matrix-composition pass. [Source: three.js `Object3D` docs on `updateMatrixWorld`/`matrixAutoUpdate`, https://threejs.org/docs/#api/en/core/Object3D.updateMatrixWorld — general behavior only, not a benchmark.]
- **Overall conclusion**: at the operation counts sized in §1 (6-10 quaternion writes, 4-6 `setValue()` calls per frame), the raw per-operation cost is negligible relative to the mixer/matrix-update/render costs the frame is already paying — consistent with the question's framing that these are "known to be cheap... even ×10" at this scale. No source contradicts this; the risk is not the per-operation cost but **allocation churn** if scratch objects aren't reused (see §4) and the compounding of many small `Math.sin`/branch calls if the system count grows unbounded (§5 addresses this).

## 4. Concrete recommended techniques

**Extend the codebase's existing allocation-reuse pattern to the procedural layer.** This codebase already establishes the habit twice: crossfade tuning (#5) reuses pre-allocated `THREE.Quaternion` instances outside the per-track loop rather than `new`-ing one per iteration, and the state layer's own crossfade runs a manual per-frame `setEffectiveWeight` ramp instead of the built-in linear fade, specifically to avoid GC churn in the hot path. This is the same pattern R3F's own docs prescribe generally:

> "This creates a new vector 60 times a second, which allocates memory and forces the GC to eventually kick in... Set up re-used objects in global or local space, now the GC will be silent." — [R3F docs, Performance Pitfalls](https://r3f.docs.pmnd.rs/advanced/pitfalls)

Concrete application to the procedural layer: every breathing/sway/gaze/audio-reactive system should hold its own **module- or ref-scoped scratch `THREE.Quaternion`/`THREE.Euler`** (created once at mount, never per-frame), matching the crossfade prototype's approach rather than introducing a new pattern. Do not allocate a `new THREE.Quaternion()` or `new THREE.Vector3()` inside `useFrame` for any of the 5-6 systems in §1.

**Composition order / additive vs. overwrite guidance.** Multiple systems (breathing + sway both touch spine; a future gaze system would touch head/neck) writing to the same bone in the same frame need a defined composition rule, not last-write-wins overwrite. Prior art from game engines with mature layered-animation systems:

- Unity's Animator layers document an explicit **additive blending mode**, where "the additive animation is based on the offset from the 1st frame of the animation to its current frame" and is applied *on top of* the base layer's result rather than replacing it — [Unity Manual, Animation Layers](https://docs.unity3d.com/6000.4/Documentation/Manual/AnimationLayers.html).
- Unreal Engine's additive animation system composites via "Mesh Space Rotation Blend," and Epic's own guidance explicitly warns about the failure mode this ticket needs to avoid: **"Multiple additive layers can interact in unexpected ways — if your breathing, lean, and aim offset all add rotation to the same spine bones, the cumulative result can push the spine into an unnatural extreme, so you should audit your additive layers for bone overlap."** — [Unreal Engine, Using Layered Animations](https://dev.epicgames.com/documentation/unreal-engine/using-layered-animations-in-unreal-engine).

Recommendation: treat each procedural system's output as a **small delta quaternion multiplied onto the bone's current (post-mixer) orientation** (`bone.quaternion.multiply(deltaQuat)`), not an absolute `.set()`/overwrite — this is the three.js-native equivalent of the additive-layer pattern above, and it composes correctly regardless of write order as long as all systems use `multiply` rather than `copy`/`set`. Where two systems target the *same* bone (breathing + sway on spine, per §1), apply them in a fixed, documented order within the single `useFrame` callback (e.g., breathing then sway then audio-reactive scale) so behavior is deterministic frame-to-frame, and — per Epic's explicit warning above — bound/clamp the combined delta magnitude so overlapping small offsets can't compound into an unnatural extreme over many frames.

**Time-slicing / staggering prior art.** Beyond the graceful-degradation mechanism in §5 (which is the primary mechanism recommended for this codebase), the general game-dev concept of splitting non-critical per-frame work across frames rather than doing it all every frame is documented as "time slicing" — e.g., Ming-Lun Chou's game-programming write-up frames it as "splitting CPU work across different frames, doing critical work every frame and splitting the rest" ([Allen Chou, "Game Programming: Time Slicing"](https://allenchou.net/2021/05/time-slicing/)), and Godot's engine proposals discuss the same idea specifically for skeletal animation ("a variable that sets the number of skipped frames, for very distant animations") — [Godot proposal #12142, "Implement animation update slicing for animations and bones"](https://github.com/godotengine/godot-proposals/issues/12142). This is the same underlying idea as §5's per-system update-rate throttling, just framed as a general technique rather than tied to a specific engine's runtime API.

## 5. Graceful-degradation recommendation

**Named prior art.** Update-rate throttling for animation under budget pressure is an established, named technique in two major engines, not a bespoke invention:

- Unity's `AnimatorCullingMode` — while primarily visibility-driven rather than time-budget-driven, establishes the precedent of selectively skipping animation evaluation (`CullUpdateTransforms` / `CullCompletely`) while keeping cheaper state-machine logic running, i.e., **tiering animation cost by importance rather than an all-or-nothing switch** — [Unity Scripting API, `AnimatorCullingMode`](https://docs.unity3d.com/ScriptReference/AnimatorCullingMode.html).
- Unreal Engine's **Update Rate Optimization (URO)** is the more directly analogous, budget-driven version: "URO essentially means skipping several frames of an animation each cycle... to reduce animation performance costs while maintaining perceived quality" — [Unreal Engine, Animation Optimization](https://docs.unrealengine.com/4.27/en-US/AnimatingObjects/SkeletalMeshAnimation/Optimization). Epic's newer **Animation Budget Allocator** generalizes this further into an explicit runtime budget: it "control[s] the tick rate of Animation Blueprint evaluations... by setting a processing budget that dynamically throttles Skeletal Mesh Component animation ticking" — [Unreal Engine, Animation Budget Allocator](https://dev.epicgames.com/documentation/unreal-engine/animation-budget-allocator-in-unreal-engine). This is the closest available named prior art to "detect budget pressure at runtime and adaptively throttle lower-priority procedural animation" — it is a budget allocator operating per-tick, exactly the shape this ticket asks about, just built for many-character scenes rather than a single avatar.

**Concrete proposal, sized to this SDK's 5-6 systems (§1):**

1. **Detection**: `useFrame(state, delta)` already receives `delta` every call — no new instrumentation is needed to observe frame-time pressure; R3F's own `useFrame` signature is the mechanism ([R3F docs, Performance Pitfalls](https://r3f.docs.pmnd.rs/advanced/pitfalls), confirming `delta` is passed for exactly this "refresh-rate independence" purpose, i.e., the loop already provides the raw material for pressure detection). A cheap runtime signal: maintain a short rolling average of `delta` (e.g., last 30-60 frames) in a ref; if the average exceeds a threshold (e.g., ~20ms, indicating sustained sub-50fps), treat the frame as "under pressure."
2. **Tiering** (which systems stay every-frame vs. degrade), based on §1's cost/perceptual-sensitivity sizing:
   - **Always every-frame, never throttled**: Blinking (system 1) — already the shipped, proven pattern, cheapest system (2 `setValue()` calls, mostly idle), and motion discontinuities in blinking are highly perceptible.
   - **Every-frame under normal conditions, first to degrade under sustained pressure**: Breathing and sway (systems 2-3) — continuous sine cycles are visually smooth even sampled at a reduced rate (e.g., every 2nd frame, ~30Hz) because the underlying motion itself is slow (multi-second periods), so a lower sample rate doesn't introduce visible stepping, unlike blinking's fast discrete motion.
   - **Cheapest to throttle aggressively**: Expression rest-state drift (system 4) — by design its *target* already changes slowly over seconds, so updating it every 3rd-4th frame (~15-20Hz) is very unlikely to be perceptible, making it the best first candidate to shed load.
   - **Tied to hook cadence, not independently throttled**: Audio-reactive amplitude (system 5) — since it only reads a scalar already computed by `useAudioLipSync`, throttling it independently doesn't save much (the expensive work is upstream); if under pressure, prefer throttling systems 2-4 first.
   - **Future**: Gaze (system 6, unspec'd) — flagged as the system most likely to eventually need its own throttling of the look-at *target* solve specifically (separate from the cheap quaternion-slerp-toward-target part, which can stay every-frame even if the target updates less often) — sized here only as a heads-up for whoever specs that ticket, not resolved.
3. **Mechanism**: implement each throttleable system with a frame-counter check (`frameCount % N === 0`) gated by the pressure signal from step 1 — i.e., `N` is 1 (every frame) under normal conditions and increases (2, 3, 4...) as sustained pressure is detected, then relaxes back down as pressure clears. This is the direct three.js/R3F-scale analog of URO's "skip several frames... each cycle" behavior cited above, applied per-system rather than per-character (since this SDK only ever renders one avatar, the allocator doesn't need Unreal's cross-character budget-sharing complexity — a much simpler fixed-tier throttle is sufficient here).
