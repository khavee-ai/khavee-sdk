<objective>
Genuinely fix the transparent-toggle bug that quick tasks 260707-0u6 (commit 5a39d51) and 260707-oyu (commit 3f4fa74) both attempted and failed to resolve — confirmed still broken via live browser testing in wp-env.

ROOT CAUSE (confirmed via live DOM inspection, not guesswork): `wordpress-plugin/includes/Admin/SettingsPage.php`'s "belt-and-braces" event-listener loop (~lines 440-447) does:

```js
el.addEventListener( 'input', rebuild );
el.addEventListener( 'change', rebuild );
```

Passing `rebuild` directly as the listener means the browser invokes it as `rebuild(event)` — the native DOM `Event` object becomes `rebuild`'s `colorOverride` parameter (line 358: `function rebuild( colorOverride )`). Since `colorOverride || ( colorEl ? colorEl.value : '#6929ff' )` (line 369) treats any truthy value as an override, and a DOM Event object is truthy, **every checkbox toggle or slider drag on any of the 6 wired fields corrupts `bgColor` into a serialized Event object** instead of a valid hex string.

Live-verified: after clicking the "Transparent floating background" checkbox, `mount.dataset.khaveeaiPreviewConfig` contained literally `"bgColor":{"isTrusted":true}` — the serialized Event, not `"#dd3333"`.

When the checkbox is then unchecked, `PreviewScene.tsx`'s container tries to set its CSS `background` to that invalid object value. Browsers silently ignore invalid CSS declarations and retain whatever was previously applied (`"transparent"`) — this is the exact "stuck transparent" symptom, and it has NOTHING to do with the Canvas/WebGL layer both prior fix attempts targeted. This also explains why dragging the camera in the preview "fixes" it: the `khaveeai-preview-camera-angle` CustomEvent handler (~line 467) calls `rebuild()` with **zero** arguments, which correctly falls through to reading `colorEl.value` — a valid string — repairing the config as a side effect.

Fix: wrap `rebuild` in each listener so it is always invoked with zero arguments, never receiving the raw Event as `colorOverride`.

Output: Corrected `SettingsPage.php` where the six belt-and-braces listeners (`khaveeai_floating_bg_color`, `khaveeai_floating_bg_transparent`, `khaveeai_floating_avatar_offset_x`, `khaveeai_floating_avatar_offset_y`, `khaveeai_floating_avatar_scale`, `khaveeai_floating_camera_rotation_y`) never leak the DOM Event into `rebuild`'s `colorOverride` param.

  <action>
In the `ids.forEach(...)` block (~lines 440-447), change:

```js
el.addEventListener( 'input', rebuild );
el.addEventListener( 'change', rebuild );
```

to:

```js
el.addEventListener( 'input', function () { rebuild(); } );
el.addEventListener( 'change', function () { rebuild(); } );
```

This ensures every one of the six wired fields (`khaveeai_floating_bg_color`, `khaveeai_floating_bg_transparent`, `khaveeai_floating_avatar_offset_x`, `khaveeai_floating_avatar_offset_y`, `khaveeai_floating_avatar_scale`, `khaveeai_floating_camera_rotation_y`) always calls `rebuild()` with zero arguments from this listener path, so `colorOverride` is always `undefined` here and `bgColor` always falls through to reading `colorEl.value` (a valid hex string) — never a DOM Event object.

Do NOT touch the `wpColorPicker` `change`/`clear` callbacks or the `irischange` handler (~lines 402-427) — those already correctly pass either a resolved color string or nothing. Do NOT touch the `khaveeai-preview-camera-angle` CustomEvent listener (~line 457-468) — it already calls `rebuild()` with zero arguments correctly.

Add a one-line comment directly above the two `addEventListener` calls explaining why the wrapper is required (the prior bug: passing `rebuild` directly leaks the Event as `colorOverride`, corrupting `bgColor`), so a future editor doesn't "simplify" it back to the bug.
