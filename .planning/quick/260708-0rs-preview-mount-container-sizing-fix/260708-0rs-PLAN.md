<objective>
Fix a real, live-confirmed layout bug affecting BOTH Settings-page preview mounts (Avatar section, added 260707-0u6; Floating Widget, added 260706-vf4): the React-rendered avatar canvas only fills a small fraction of its mount box (~140px of a 340px box for Avatar; ~180px of a 520px box for Floating), leaving a large blank "dead space" below it, INSIDE the same bordered/rounded preview card.

ROOT CAUSE (confirmed via live `getBoundingClientRect()` inspection in wp-env, not guesswork): neither `render_avatar_section_preview_mount()` nor `render_floating_preview_mount()` (in `wordpress-plugin/includes/Admin/SettingsPage.php`) sets `containerWidth`/`containerHeight` in the JSON config they write to `data-khaveeai-preview-config`. `PreviewScene.tsx`'s `containerStyle` (lines ~251-257) only sets an explicit CSS `width`/`height` on its wrapping div when `config.containerWidth`/`config.containerHeight` (or `config.fullWidth`) are present:

```js
if (config.fullWidth) {
  containerStyle.width = "100%";
} else if (config.containerWidth && config.containerWidth > 0) {
  containerStyle.width = `${config.containerWidth}px`;
}
if (config.containerHeight && config.containerHeight > 0) {
  containerStyle.height = `${config.containerHeight}px`;
}
```

Without an explicit height, the div has no resolvable height for the R3F `<Canvas>`'s internal `height:100%` wrapper to inherit (percentage heights require an ancestor with an explicit height), so the canvas falls back close to its intrinsic default size (~150px tall) instead of filling the mount box. The Gutenberg block editor's own preview (`wordpress-plugin/src/editor.js`) never hits this bug because it always passes `containerWidth`/`containerHeight` from the block's own attributes — this is exactly the "edit page preview" the user is referencing as the correct reference behavior.

**User-visible symptom this explains:** the Avatar section's live preview looked like a small avatar sitting in the top of its box with a large blank area below — the SAME "small-avatar + big-empty-area" shape as the Floating Widget's preview (which fills that empty area with a separately-appended static mock chat below the box). This made the Avatar preview look like a mis-configured floating widget even though no chat component is actually rendered inside it (confirmed live: no `.khaveeai-layout` or `.khaveeai-chat` element exists inside `#khaveeai-avatar-preview` — `config.chatShow` is correctly never set in either mount's config).

Fix: add `containerWidth`/`containerHeight` (matching each mount div's actual pixel dimensions, already hardcoded inline on the mount divs themselves) to both config arrays, so the inner container — and therefore the R3F Canvas, which resizes reactively via ResizeObserver — genuinely fills the whole box in both previews. This is a pure sizing fix:
- Avatar section preview → avatar fills the whole 280x340 box, no dead space, reads as "just avatar" (what the user wants, matching the block editor's own preview behavior).
- Floating Widget preview → avatar fills the whole 360x520 box, and the mock chat (already a separate DOM element rendered immediately after the mount div by `render_floating_preview_mock_chat()`) now reads as its own clearly-distinct block directly below the avatar box, rather than ambiguously bleeding into a shared blank area.

Output: `SettingsPage.php`'s two config arrays gain `containerWidth`/`containerHeight` keys. No changes to `PreviewScene.tsx`, `mountPreview.tsx`, or any build artifact — this is a pure JSON-config addition consumed by already-existing, already-correct React logic.
</objective>
