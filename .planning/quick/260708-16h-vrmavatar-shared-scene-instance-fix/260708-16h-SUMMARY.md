# Quick Task 260708-16h: VRMAvatar Shared-Scene Instance Fix Summary

**Replaced `@react-three/drei`'s globally-cached `useGLTF` with a per-instance `useLoadVRM(src)` hook (fresh `GLTFLoader.parseAsync()` + `VRMLoaderPlugin` per component instance) so multiple simultaneous `<VRMAvatar src="same-url">` instances each get their own independent scene/VRM object instead of one instance stealing the model from the other.**

## Performance

- **Duration:** ~7 min (Task 1 + Task 2)
- **Completed:** 2026-07-08
- **Tasks:** 2 of 3 (Tasks 1-2 auto; Task 3 is a `checkpoint:human-verify` requiring live browser interaction, handed off to the orchestrator)
- **Files modified:** 3 (1 source, 2 generated wordpress-plugin bundles)

## Accomplishments

- Root-caused bug fixed: `VRMAvatar.tsx` no longer calls `useGLTF` for the avatar model itself (animation file loading via `useAnimationFiles`/`useFBX`/`useGLTF` is untouched, out of scope per plan).
- New `useLoadVRM(src)` hook: module-level `glbBufferCache: Map<string, Promise<ArrayBuffer>>` fetches each URL's GLB at most once; each component instance runs its own `new GLTFLoader()` + `loader.register(...VRMLoaderPlugin...)` + `parseAsync()`, producing a genuinely independent `scene`+`VRM` pair with no manual bone re-linking.
- Downstream render/effects audited and guarded for the now-possibly-`undefined` loading state (this was previously guaranteed-defined by `useGLTF`'s Suspense contract): the VRMUtils cleanup effect now checks `!currentVrm || !scene`, and the render path only mounts `<primitive object={scene}>` when `scene` is defined, keeping the wrapping `<group>` always mounted.
- GPU resource disposal added: `VRMUtils.deepDispose()` runs both in the effect cleanup (normal unmount/src-change) and when a parse resolves after the component already unmounted/src-changed (cancellation-guard path) - required because resources are no longer shared across instances.
- All consuming packages verified to build cleanly in dependency order: `@khaveeai/core`, `@khaveeai/react`, `@khaveeai/providers-openai-realtime` (transitive dependency of wp-bundle, not explicitly listed in the plan's build order but required for it to resolve), `@khaveeai/wp-bundle`.
- `wordpress-plugin/build/khaveeai-preview.js` and `khaveeai-bundle.js` regenerated; STUDIO-02 safety grep (`getUserMedia|ephemeral`) count unchanged at `0` (baseline `0` too - no realtime-related code pulled in).

## Decisions Made

- **GLTFLoader import path:** `three/examples/jsm/loaders/GLTFLoader.js` (not `three-stdlib`, which drei's internal `useGLTF` uses). `three-stdlib` is not a declared dependency of `@khaveeai/react`, while `three` already is, and this file already deep-imports `three/src/math/MathUtils.js` - matching that existing precedent avoided adding a new dependency.
- **Hook naming:** the new internal per-instance-parse hook is named `useLoadVRM` (not `useVRM`) specifically to avoid colliding with the existing exported `useVRM()` function later in the same file (context-based, returns `{ vrm }` from `useKhavee()`).
- **Loading-state guard placement:** rather than change the component's public API/props, all defined-ness handling is internal - `scene`/`currentVrm` are now `| undefined` locally, with guards added only where downstream code previously assumed Suspense-guaranteed definedness.

## Live Verification (performed by orchestrator via Chrome browser automation)

Confirmed in wp-env: both the Avatar-section and Floating-Widget previews render their avatars simultaneously and independently — the primary bug (one instance stealing the model from the other) is fixed. Orbit-dragging one preview's camera left the other's pose/angle untouched, confirming genuine independence (not just simultaneous visibility).

**A second regression was found during this same verification pass and fixed as part of this task:** both avatars initially loaded in a raw T-pose (bind pose) instead of the expected idle animation stance. Root cause: the "animation switching" `useEffect` in `VRMAvatar.tsx` only depended on `[currentAnimation]`, which never changes after mount (`KhaveeProvider` defaults it to `"idle"` once and it stays there). Under the old Suspense-based `useGLTF`, the animation mixer was always already created by the time this effect first ran (Suspense guaranteed synchronous readiness), so it worked by coincidence. `useLoadVRM`'s async loading means the mixer now becomes ready on a LATER render, and since the effect had no way to know to retry, the idle animation was never applied.

**Fix applied (commit `107a562`):** added `processedClips` to that effect's dependency array, so it retries once the mixer/clips actually become available:
```js
}, [currentAnimation, processedClips]);
```
Rebuilt `@khaveeai/react` (`tsc` clean) and `@khaveeai/wp-bundle` (clean, STUDIO-02 safety assertion passed) after this fix. Re-verified live: both previews now show the natural idle stance, not T-pose.
