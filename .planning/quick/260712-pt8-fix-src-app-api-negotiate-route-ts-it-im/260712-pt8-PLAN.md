<objective>
Fix `src/app/api/negotiate/route.ts` so it implements the ephemeral-token-minting contract `OpenAIRealtimeProvider.connect()` actually expects, instead of the stale raw-SDP-relay contract it implements today. This was surfaced by a live 400 error: `OPENAI API error: {"error":{"message":"Failed to parse offer: failed to unmarshal SDP: sdp: syntax error at pos 1: \"\\\"\""...}}`.

Root cause (confirmed by direct source inspection, not assumption): `OpenAIRealtimeProvider.connect()` (`packages/providers/openai-realtime/src/OpenAIRealtimeProvider.ts:159-186`), when `useProxy` is set, POSTs `{ sessionConfig }` as JSON to `proxyEndpoint` and expects back a JSON `ProxyTokenResponse` (`{ data: { ephemeralToken, sessionId } }` or the flat equivalent) containing an OpenAI ephemeral session token. The provider then makes its OWN direct client-side fetch to `https://api.openai.com/v1/realtime/calls` with the SDP offer, using that ephemeral token as the bearer.

But `src/app/api/negotiate/route.ts` today does something entirely different: it reads the whole POST body as raw text (`await request.text()`), assumes it IS an SDP offer, and forwards it verbatim to OpenAI's OLD single-shot endpoint (`https://api.openai.com/v1/realtime?model=gpt-4o-realtime-preview-2024-12-17`). Since the client actually sent `JSON.stringify({ sessionConfig })`, the route forwards that JSON blob to OpenAI's SDP parser, which chokes on the `"` at byte offset 1 (the second character of `{"sessionConfig":...`, 0-indexed) — exactly matching the reported error.

This exact mismatch is already documented in this repo: README.md:130 ("the example negotiate route in this repo... predates that contract and returns a different shape"), and STATE.md:88 ("src/app/api/negotiate/route.ts is explicitly NOT the reference pattern for this route — it implements a different SDP-relay contract"). The correct reference implementation already exists in this repo, built and live-verified for the WordPress plugin's Phase 6 work: `wordpress-plugin/includes/TokenProvider/OpenAiDirectTokenProvider.php`.

Purpose: Every demo page using `OpenAIRealtimeProvider` with `useProxy: true` (`src/app/openai/page.tsx`, the newly-added `src/app/openai-avatar-test/page.tsx`, and the generic-demo family) is currently broken because of this one route. This is the actual root blocker preventing the OpenAI Realtime + lipsync demo from connecting at all.
Output: `src/app/api/negotiate/route.ts` rewritten to mint and return an ephemeral token instead of relaying SDP.
</objective>

<context>
Confirmed contract, ported from the live-verified PHP reference (`wordpress-plugin/includes/TokenProvider/OpenAiDirectTokenProvider.php`):

- **OpenAI endpoint:** `POST https://api.openai.com/v1/realtime/client_secrets`
- **Request headers:** `Authorization: Bearer <OPENAI_API_KEY>`, `Content-Type: application/json`
- **Request body:** `{ "session": <sessionConfig> }` — the session config MUST be nested under a top-level `"session"` key. Posting it unwrapped is rejected with `400 Unknown parameter` for every field (confirmed via live curl during Phase 6, per STATE.md:75).
- **OpenAI 2xx response body:** `{ "value": "<ephemeral token string>", "session": { "id": "<session id>", "expires_at": <unix ts>, ... } }`
- **What our route must return to the client** (matching `ProxyTokenResponse` in `packages/providers/openai-realtime/src/OpenAIRealtimeProvider.ts:17-26`): `{ "data": { "ephemeralToken": "<value>", "sessionId": "<session.id>" } }`

Client request shape our route receives (from `OpenAIRealtimeProvider.connect()`, line 162-166): `POST` with `Content-Type: application/json`, body `{ "sessionConfig": {...} }` — note the client wraps it in a `sessionConfig` key; our route must extract `body.sessionConfig` and re-wrap it as `{ session: sessionConfig }` before forwarding to OpenAI (two different wrapper keys at two different hops — this is intentional and matches the PHP reference's `mint_session(array $session_config, ...)` taking the already-unwrapped config and doing its own `{ session: $session_config }` wrap).

Security pattern to preserve from the PHP reference (D-09/D-10 in that file's docblock): the real `OPENAI_API_KEY` must only ever appear in the outbound `Authorization` header to OpenAI, never echoed back to the client. On any OpenAI/network failure, log the real detail server-side (`console.error`) but return a generic error to the caller — do not leak upstream response bodies to the browser.
</context>
