# 260714-3b1: WP Knowledge Base Admin CRUD — Summary

## What was built

Full document management (list, add, delete) for the WordPress plugin's knowledge-base feature, replacing the previous read-only "manage on the platform dashboard" status message on the Settings page.

**Task 1 — `wordpress-plugin/includes/Platform/KnowledgeClient.php`**
Added two public static methods mirroring `list_documents()`'s exact structure (try/catch(\Throwable), `X-API-Key` header, `TIMEOUT`, `data`-shape parsing, generic non-leaking error strings):
- `insert( string $key, string $content, array $metadata = array() ): array` — POSTs JSON body `{content, metadata}` via `wp_remote_post`, accepts HTTP 200 or 201, returns `{ok, document, error}` with `document` = `$body['data']` (a single doc object).
- `delete( string $key, string $id ): array` — `wp_remote_request()` with `method => DELETE` against `BASE_URL . '/' . rawurlencode($id)`, accepts HTTP 200 or 204, returns `{ok, error}` (no body parsing, since a 204 has no body).
`search()`, `list_documents()`, and `BASE_URL` were left untouched.

**Task 2 — `wordpress-plugin/includes/Rest/KnowledgeAdminController.php` (new) + `wordpress-plugin/includes/Plugin.php`**
New REST controller in namespace `Khavee\Plugin\Rest`, mirroring `KnowledgeSearchController`'s shape (`OPTION_NAME` constant, private `respond()` helper with `Cache-Control: no-store`). Registers three routes under `khaveeai/v1`, **all** gated by a shared `check_permission()` callback (`current_user_can('manage_options')`) — never `__return_true`:
- `GET /knowledge-admin` — list documents (optional `limit`, default 50, clamped to 100).
- `POST /knowledge-admin` — create a document; rejects empty/blank `content` with 400 `invalid_content`; content capped at 20,000 chars; `metadata` accepts an array or a JSON string, normalized to an array.
- `DELETE /knowledge-admin/(?P<id>[^/]+)` — delete by id.

Each callback reads `platform_api_key` from the `khaveeai_settings` option; if unset, responds 400 `no_platform_key` (an admin-context config error, unlike the public search route's silent-empty behavior). On `KnowledgeClient` failure, responds 502 `request_failed` (a generic code — the client's own error strings are already generic, but the boundary stays clean and nothing upstream-specific crosses it).

`Plugin::boot()` now imports `Khavee\Plugin\Rest\KnowledgeAdminController` and registers it on `rest_api_init` immediately after the existing `KnowledgeSearchController` wiring, with a comment contrasting the two routes' auth posture. No other wiring (`SessionController`, `AvatarRenderer`, etc.) was touched.

**Task 3 — `wordpress-plugin/includes/Admin/SettingsPage.php`**
`render_knowledge_base_field()` keeps the existing `knowledge_base_enabled` checkbox exactly as before. When no `platform_api_key` is set, the original "Requires a Khavee Platform API Key" description still renders (unchanged, early `return`). When a key **is** set, it now renders a `<div id="khaveeai-kb-manager">` panel containing:
- `<div id="khaveeai-kb-list">` — filled by JS with the fetched documents.
- An "Add document" form (`<textarea id="khaveeai-kb-content">`, optional `<input id="khaveeai-kb-metadata">`, `<button type="button" id="khaveeai-kb-add">` — `type="button"` so it never submits the surrounding settings `<form>`).
- `<p id="khaveeai-kb-status" aria-live="polite">` for success/error text.

None of these fields use `name="khaveeai_settings[...]"` — they're managed purely via the REST API, so `sanitize_settings()` is untouched.

`enqueue_settings_assets()` now also calls `wp_localize_script('wp-color-picker', 'khaveeaiKb', {root, nonce})` (reusing the already-enqueued `wp-color-picker` handle, same convention the existing floating-preview inline JS uses) and attaches a second `wp_add_inline_script('wp-color-picker', $kb_js, 'after')` block containing vanilla JS that:
- On DOM ready, if `#khaveeai-kb-manager` exists, GETs `khaveeaiKb.root` with `X-WP-Nonce` and renders `data[]` into `#khaveeai-kb-list` via `textContent`/`createElement` (no `innerHTML` of server content).
- Wires the delete button per row (`DELETE {root}/{id}` with the nonce), removing the row on success.
- Wires the Add button (`POST {root}` with `{content, metadata}` JSON; metadata input is `JSON.parse`'d, falling back to `{note: raw}` on parse failure, or `{}` when empty), clearing inputs and reloading the list on success.
- All fetches send `X-WP-Nonce`; POST additionally sends `Content-Type: application/json`. Failures show a generic status message, never a raw response body.

The floating-preview inline JS, color-picker enqueue, `add_menu_page`, `register_settings`, and `sanitize_settings()` were not modified. All existing element IDs the floating-preview JS depends on remain intact.

## Live browser verification (follow-up session)

Tested end-to-end in `wp-env` against a local `core-api` instance (production `api.platform.khavee.ai` doesn't have the `sdk/knowledge*` routes deployed yet, confirmed via a direct 404). Two real bugs surfaced and were fixed:

1. **Knowledge Base section never rendered at all.** `render_knowledge_base_field()` was registered via `add_settings_field()`, but this page renders through a hand-assembled manual layout (`render_section_heading()` / `render_form_table_row()` calls), not `do_settings_sections()`. No call to render the knowledge-base row existed in that manual layout — the toggle (and now the document manager) was invisible on the page since it was first introduced, in an earlier session, well before this quick task. Fixed by adding the missing card to the manual layout.
2. **Adding a document with blank metadata always 400'd.** `wp_json_encode(array())` serializes an empty PHP array as JSON `[]`, but core-api validates `metadata` with `@IsObject()`, which rejects arrays. Fixed by casting to `stdClass` when `$metadata` is empty, forcing `{}`.

After both fixes, verified via real network requests (not just visual inspection):
- `GET /wp-json/khaveeai/v1/knowledge-admin` → 200, correct list
- `POST /wp-json/khaveeai/v1/knowledge-admin` → 201, document appears in the list immediately
- `DELETE /wp-json/khaveeai/v1/knowledge-admin/{id}` → 200, document removed from the list immediately

**Still not verified:** non-admin/logged-out denial (403) on the three routes — not exercised this session, low risk since `check_permission()`'s `current_user_can('manage_options')` gate is straightforward and unchanged from the original implementation.

**Minor cosmetic gap noticed, not fixed:** after deleting the last remaining document, the list area goes blank instead of showing "No documents yet." (that empty-state message is only produced by the initial `renderList()` on page load; the delete handler just removes the DOM row rather than re-rendering). Low priority — no functional impact, `loadList()` on next page load will show it correctly.
