<objective>
Eliminate redundant OpenAI embedding API calls in `@khaveeai/providers-pgvector` by letting callers reuse one pre-computed embedding across multiple similarity searches.

Purpose: khavee-app's RAG lookup does a two-threshold fallback (0.3 -> 0.15) plus multi-query fusion, which today re-embeds identical text and costs an extra network round-trip inside a live voice pipeline. The user waits for that latency.

Output: A new public `searchByEmbedding()` method on `PgVectorProvider`, an internal `runVectorQuery()` helper so the search SQL lives in exactly one place, a dependency-free verification script, a patch version bump, and README docs.

Scope guard: SDK package only (`packages/providers/pgvector`). The consumer-side change in khavee-app is a separate follow-up and MUST NOT be attempted here. No npm dependencies may be added. No push, tag, or publish.
</objective>

1. Add `private async runVectorQuery(vec: string, topK: number, threshold: number, metadataFilter?: Record<string, unknown>): Promise<PgVectorSearchResult[]>`. 2. Rewrite `searchDocuments` to: `const embedding = await this.embed(query); return this.runVectorQuery(this.toVectorLiteral(embedding), topK, threshold, metadataFilter);`. Keep its existing parameter list and defaults (`topK = this.defaultTopK`, `threshold = this.defaultThreshold`) exactly as-is.

3. Leave `search()` untouched — it still delegates to `searchDocuments`.

4. Add `async searchByEmbedding(embedding: number[], topK: number = this.defaultTopK, threshold: number = this.defaultThreshold, metadataFilter?: Record<string, unknown>): Promise<PgVectorSearchResult[]>`. It validates the embedding, then returns `this.runVectorQuery(this.toVectorLiteral(embedding), topK, threshold, metadataFilter)`. It MUST NOT call `this.embed()`.

5. Validation inside `searchByEmbedding`, before building the literal (guards the one public entry point that accepts a raw vector; without it a malformed array reaches Postgres as an unparseable vector literal and surfaces as an opaque driver error):

   - `length !== this.embeddingDimensions` -> `throw new Error(\`Embedding dimension mismatch: got \${embedding.length}, expected \${this.embeddingDimensions}\`)`
   - any element fails `Number.isFinite` -> `throw new Error("Embedding contains non-finite values (NaN/Infinity)")`
   Throw plain `Error` with the offending value in the message, matching the package's existing error style (`STTClient`/`ChatClient` convention: plain Error, context baked into the message, no typed hierarchy).

JSDoc on `searchByEmbedding` per package convention (`/** ... */` with `@param`/`@throws`): state that it runs the identical similarity query as `searchDocuments` but skips the embedding API call, and give the intended usage — embed once with `embed(text)`, then call `searchByEmbedding` repeatedly (e.g. a 0.3 threshold attempt then a 0.15 retry, or the same vector against different metadata filters) to avoid re-paying the embedding round-trip.    with a short doc comment explaining it reuses a pre-computed embedding. Add nothing else to the interface; do not touch `search()`.
