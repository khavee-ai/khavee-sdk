<objective>
Make `@khaveeai/providers-pgvector`'s bulk-insert / CSV-import path embed in batches instead of one API call per row.

Purpose: `bulkInsertDocuments()` currently calls `insertDocument()` per row, which calls `embed()` per row. A 267-row CSV import fires 267 separate OpenAI embeddings requests (parallelized only `concurrency`-wide, default 5 — so ~54 sequential round-trips). OpenAI's embeddings endpoint accepts an array `input`, so the same import can be done in 3 requests.

Output: A private `embedBatch()` helper, a private `insertDocumentWithEmbedding()` so the INSERT SQL lives in exactly one place, a rewritten `bulkInsertDocuments()` that batches embeddings while preserving per-row error granularity, a dependency-free verification script, README docs, and a patch version bump.

Scope guard: SDK package only (`packages/providers/pgvector`). Do NOT touch khavee-app or any other package/repo. No new npm dependencies, no test framework. No push, tag, or publish.

Non-breaking guard: `embed()`, `insertDocument()`, `bulkInsertDocuments()`, and `importCSV()` keep their exact public signatures and observable behavior. `BulkInsertResult` shape is unchanged. This is a transparent internal optimization.
</objective>

1. Add a private readonly field next to the other private fields: `private readonly embeddingBatchSize = 100;` with a doc comment explaining it is an internal tuning constant, not a config option — 100 texts per request is well under OpenAI's per-request array-size limit for `text-embedding-3-small`/`-large` regardless of individual text length, so a single request can never blow the array/token ceiling. 2. Add `private async embedBatch(texts: string[]): Promise<number[][]>` in the Embedding section, below `embed()`:
   - Return `[]` immediately for an empty input array.
   - Chunk `texts` into groups of `this.embeddingBatchSize` so callers never have to think about API limits.
   - Per chunk, make ONE `await this.openai.embeddings.create({ model: this.embeddingModel, input: chunk })`.
   - Sort a copy of `res.data` by its `index` field ASCENDING before mapping to `embedding`. Do not mutate `res.data` in place, and do not assume array order is preserved — cheap defensive insurance against a silent content/embedding mismatch that would corrupt the knowledge base with no visible error.
   - If the sorted length !== the chunk length, throw `new Error(\`Embedding batch size mismatch: sent \${chunk.length} texts, received \${sorted.length} embeddings\`)` — a partial response must fail loudly rather than shift every subsequent row's embedding by one.
   - Accumulate into a flat `number[][]` whose order matches the input `texts` order exactly, and return it.
   - Do NOT catch API errors here — let them propagate. `embedBatch` has no knowledge of `BulkInsertResult`/row numbering; the caller owns error attribution.
   - JSDoc per package convention (`/** ... */` with `@param`/`@returns`/`@throws`), noting it is private, internally chunked, and order-preserving.

3. Add `private async insertDocumentWithEmbedding(content: string, metadata: Record<string, unknown>, embedding: number[]): Promise<PgVectorDocument>` in the Insert section. 4. Rewrite `insertDocument` to: `const embedding = await this.embed(content); return this.insertDocumentWithEmbedding(content, metadata, embedding);`. Keep its exact parameter list, defaults (`metadata: Record<string, unknown> = {}`), return type, and JSDoc.

5. Rewrite `bulkInsertDocuments(rows, concurrency = this.defaultConcurrency)` — signature and return type UNCHANGED — as an outer chunk loop over `this.embeddingBatchSize` and an inner insert loop over `concurrency`:
   - Guard the insert-parallelism value once at the top: `const insertConcurrency = Math.max(1, Math.floor(concurrency) || 1);` and use it for the inner loop stride. A zero/negative/NaN `concurrency` previously produced an infinite loop; this guard is a defensive fix, not a behavior change for any valid input.
   - Outer loop: `for (let i = 0; i < rows.length; i += this.embeddingBatchSize)`, `const chunk = rows.slice(i, i + this.embeddingBatchSize)`.
   - Declare `let embeddings: number[][];` then `try { embeddings = await this.embedBatch(chunk.map((r) => r.content)); } catch (err) { ... continue; }`. In that catch, attribute the failure to EVERY row in the chunk: for each `idx` in the chunk, `result.failed++` and `result.errors.push({ row: i + idx + 1, reason: String(err) })`, then `continue` to the next chunk. One chunk's embedding failure must never abort the whole import.
   - Inner loop over the chunk in slices of `insertConcurrency`: `for (let j = 0; j < chunk.length; j += insertConcurrency)`, `await Promise.all(slice.map(async (row, k) => { ... }))`. Inside, `const rowNum = i + j + k + 1;` and the embedding for that row is `embeddings[j + k]`. Each row's insert is individually try/caught: on success `await this.insertDocumentWithEmbedding(row.content, row.metadata ?? {}, embeddings[j + k]); result.inserted++;`, on failure `result.failed++; result.errors.push({ row: rowNum, reason: String(err) });`. This preserves the exact current per-row INSERT error granularity — a constraint violation on one row must not take down its siblings.
   - Row numbering stays 1-indexed against the ORIGINAL `rows` array in every error entry.
   - Never call `this.insertDocument(...)` from here — that would re-embed and defeat the whole change.
   - Update the JSDoc: embeddings are batched (up to `embeddingBatchSize` texts per API call); `concurrency` now controls how many parallel INSERT statements run per chunk, not how many parallel embedding requests are in flight.

6. In `types.ts`, update ONLY the doc comment on `PgVectorConfig.defaultConcurrency` and on `CSVImportOptions.concurrency` to reflect the new meaning ("Max parallel INSERT statements per embedding batch during bulk insert (default: 5)"). Do NOT add, rename, or remove any field — no new config option is introduced by this plan.

7. Keep the existing `// ── Section ──` divider style throughout. No changes to `index.ts` (the class is already exported; both new methods are private).
